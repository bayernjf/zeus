# 企业形态裁定稿：隔离实例 vs 同实例多租户（deferred #41）

> 状态：**决策待定稿 v0.1（2026-10-08）**——本稿整理现状代码事实、决策矩阵与推荐，**方向由用户拍板**；拍板后本稿转"方向已固化"并出开工面清单。实施进度记 [handoff.md](../handoff.md)，本文只写设计与裁定。
> 上游：[deferred-items.md](deferred-items.md) #41（议题与 A/B 代价原文）、#18（MCP 暴露侧 actor 判定，已销项）、[design-realm.md](design-realm.md)（数据域与租户模型）、[design-execution-delegation.md](design-execution-delegation.md)（跨域一次性授权）。

## 1. 决策问题

一家公司用 Zeus 时，是**每个客户（或每个团队）一套进程**（隔离实例，A），还是**一套进程内跑多个租户**（同实例多租户，B）。此决定影响认证面、状态文件形状、备份清单粒度与运维模型。

## 2. 现状代码事实（2026-10-08 实测）

| 事实 | 位置 | 含义 |
|---|---|---|
| 租户**模型**已在库内 | `src/realm/authorization.ts` `#decideRealmAccess`（三级范围 org/部门/成员） | 授权判定是纯函数，与部署形态解耦 |
| 进程**只有一套身份** | `src/http/server.ts` H2 全操作面挂载条件为单个 `ZEUS_INTERNAL_TOKEN` | 无 per-tenant principal |
| **MCP 面已有会话级 actor 原语** | `src/http/server.ts`：`x-zeus-realm-actor` header，effectiveRealmIds = 宿主白名单 ∩ actor.realmIds，仅可收窄（Active work 144 实现，deferred #18 已于 2026-10-08 销项） | 内核"主体"概念已有雏形，但只覆盖 MCP 暴露侧 |
| 路由规模 | feature-inventory §2.1：**92 条 HTTP 路由（3 公开 + 89 bearer）** | B 形态需逐条决定租户可见性 |

**关键新事实（相对 #41 登记时）**：#41 的翻转条件问"#18 在 A 形态下能否廉价收口"。2026-10-08 的答案是——**已在 MCP 面廉价收口**（会话级 actor 仅可收窄宿主白名单，零 SDK 依赖、11 例测试全绿）。这说明"主体"原语可做且不贵，但当前只落地在 MCP 暴露侧；H1/H2/H3 三面仍是单一 bearer。

## 3. 决策矩阵（A vs B）

| 维度 | A 隔离实例 | B 同实例多租户 |
|---|---|---|
| 认证面 | **零改动**（单 bearer 现状即 A 形态） | **先重做**：单一 bearer → per-tenant principal，H1/H2/H3 三面按主体裁剪 |
| 状态文件 | 每实例独立卷，形状不变 | 快照按租户分片 + 证明跨片不可读 |
| 审计/备份 | 每实例独立 JSONL/备份清单，粒度=实例 | 按租户分片；备份清单粒度细化到租户 |
| 路由面 | 92 条全不动 | 92 条逐条决定租户可见性；`/api/audit`、`/api/domains`、`/api/roster` 等全量视图全部加范围 |
| 运维 | 部署数随客户线性增长（密钥/状态卷/备份计划/`ZEUS_*` 配置各一套），无跨客户盘点/升级看板 | 单套部署、集中运维 |
| 计费（#4） | 需另做多实例计量层 | 跨租户计量直接可得 |
| 风险形状 | 数据域隔离由**进程边界**保证（判定代码出 bug 也越不过去）；跨租户事故最坏限制在单进程内 | 一次判定缺陷可能跨租户泄漏，风险集中在共享判定代码 |
| 差异化主张 | "自带 Agent 进公司"无需额外解释（用户实例本就没接企业域） | 需解释多租户可见性边界 |

## 4. 触发条件与翻转条件评估（2026-10-08 现测）

- **触发条件**：① 出现第一个明确要求共享一套部署的企业用户且合规允许同进程内观察到其他租户；② 每实例运维成本成为签约障碍。**均未出现**。
- **翻转条件**（#41 原文："若 #18 在 A 形态下也无法廉价收口，说明主体迟早要在内核里做，不如一次做完 B"）——**已部分兑现但不足翻转**：MCP 面 actor 原语证明"主体"可廉价做，但这恰好构成"先 A、将来升 B 有地基"的论据，而非"现在就做 B"的论据——B 的其余代价（92 条路由裁剪、状态/审计/备份分片、全量视图加范围）与触发条件无关，触发前是纯沉没成本。

## 5. 推荐：维持 A 为默认形态，并记录"升 B"路径（待用户拍板确认）

推荐依据：
1. 触发条件未到，B 的全部代价在触发前是沉没成本；
2. A 下现有配置面、路由面、状态形状零改动（现状即 A）；
3. **MCP 面会话级 actor 原语已就位**——若未来触发 B，它是 per-tenant principal 的地基（把 `x-zeus-realm-actor` 的收窄语义从 MCP 面推广到 H1/H2/H3 面，是 B 的认证面重做的起点），升级路径平缓；
4. 设计约束 4（个人域与企业域不互通）在 A 下由进程边界保证，符合"先保边界、再谈集约"的次序。

## 6. 开工面（拍板后按选择执行）

**若确认 A**（推荐）：内核零改动。开工面 = 实例编排层——多实例部署模板（每实例一套 `ZEUS_*`/密钥/状态卷/备份计划）、实例生命周期与升级滚动操作手册、跨实例盘点看板设计（E10 平台工程向）。此为仓库外/部署向工程，可与真机部署（E10.2）合并推进。

**若改选 B**：开工面 = per-tenant principal 重构——① 认证面：H1/H2/H3 三面从单一 bearer 改为按主体裁剪（MCP 面 actor 原语推广为内核级原语）；② 路由面：92 条逐条决定租户可见性，全量视图（audit/domains/roster）加范围；③ 状态面：快照/审计 JSONL/备份清单按租户分片 + 跨片不可读证明；④ 验收：跨租户串读审计为 fail-closed 断言族。工作量约为 A 的 5–10 倍，且应在触发条件出现后立项。
