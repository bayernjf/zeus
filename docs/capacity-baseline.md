## 1. 这是什么、不是什么

- **是**：Zeus 内核（Orchestrator → Dispatcher → undici fetch → 回环 HTTP；场景 C 额外经过 Fastify H2 门面）在**模拟执行 Agent 群**下的扇出/并发/门面/取消能力基线，量化 fan-out/merge/aggregate、HTTP 门面与取消传播自身开销，验证无分支丢失、无取消丢失、指标峰值可信。
- **不是**：真实执行 Agent 容量。mock 执行 Agent 固定 50ms「思考延迟」（场景 D 为 5ms）、无 LLM 推理、无跨网 RTT、无鉴权后端。真实场景的延迟与吞吐由执行 Agent（LLM）和网络主导，本文数字只界定 **Zeus 自身不是瓶颈的区间**。
- 本机基准**负载敏感**，高负载点（64 扇出 / 32 并发意图）p95 波动较大；下列数字为 warmup 后独立复跑的区间，不是性能承诺。背压 / 有界队列仍为 deferred #9（触发条件：≥3 真实执行 Agent 压测）。

## 3. 场景 A：单意图扇出宽度

一个意图并行扇出 N 个执行 Agent（每执行 Agent 50ms）。理想并行时墙钟 ≈ 50ms（与 N 无关）；串行则为 50N ms。

| 扇出宽度 N | 墙钟 p50（两次复跑区间） | 墙钟 p95 区间 | 并行效率（50/p50） |
|---|---|---|---|
| 1 | 55–57 ms | 59–62 ms | 0.88–0.91 |
| 2 | 55–56 ms | 57–72 ms | 0.90–0.91 |
| 4 | 56–58 ms | 58–63 ms | 0.87–0.89 |
| 8 | 56–57 ms | 59–63 ms | 0.88–0.90 |
| 16 | 57–65 ms | 60–68 ms | 0.77–0.87 |
| 32 | 65–68 ms | 70–84 ms | 0.73–0.78 |
| 64 | 75–76 ms | 84–129 ms | 0.65–0.67 |

**读数**：
- 宽度 **1–16 墙钟稳定在 ~55–65ms**，与单执行 Agent 50ms 几乎持平——并行扇出成立，内核 fan-out/合并/聚合在该量级附加开销约 **5–15ms**。
- **32–64** 回环连接与事件循环调度开销开始可见（p50 65–76ms，p95 尾延迟上升），但相对串行（64×50 = 3200ms）仍是数量级的优势。
- 结论：**单意图并行扇出 16 个执行 Agent 是本机可舒适支撑的量级**；32+ 可用但应配合 deferred #9 的有界队列在真机重新标定。

## 4. 场景 B：并发意图吞吐（内核直调）

C 个意图**同时**发起，每个意图扇出 4 个执行 Agent（50ms），执行 Agent 在 64 个槽位间复用（与真实多租户复用一致）。

| 并发意图 C | 总分支数 | 总墙钟区间 | 单意图延迟 p95 区间 | 吞吐（意图/秒） | metrics 峰值在途 |
|---|---|---|---|---|---|
| 1 | 4 | 54–63 ms | 54–63 ms | 16–19 | 4 |
| 4 | 16 | 59–62 ms | 57–61 ms | 65–68 | 16 |
| 8 | 32 | 63–64 ms | 61–62 ms | 125–127 | 32 |
| 16 | 64 | 72–82 ms | 67–75 ms | 195–222 | 64 |
| 32 | 128 | 79–91 ms | 73–78 ms | 351–404 | 128 |

**读数**：
- **128 个分支同时在途，全部 completed、零分支丢失**（每点 `finishedBranches === totalBranches`）；`ConcurrencyMetrics.maxInFlight` 准确捕获 4/16/32/64/128 峰值。
- 32 并发意图下单意图 P95 仍在 **~80ms**（仅比单意图多 ~20–25ms），mock 回环吞吐约 **350–400 意图/秒**——该数字主要被人为 50ms think 决定，真实场景会低得多，此处仅证明内核调度在 128 并发分支下不构成瓶颈。
- 当前为无界 `Promise.all`（无背压）；128 并发在 mock 下健康，**真实执行 Agent 的连接/限流约束必须在 deferred #9 落地有界队列后，于真机重新压测**。

## 5. 场景 C：H2 驱动门面全链路吞吐（v0.2 新增）

与场景 B 同负载，但意图从**真实 HTTP 门面**进入：`POST /api/intents`（bearer 鉴权 → Fastify 路由 → JSON 解析 → 同一 Orchestrator/Dispatcher → mock farm → JSON 序列化），走 127.0.0.1 TCP。与 B 的差值即**门面 + 鉴权 + JSON 往返开销**。

| 并发意图 C | 总分支数 | 总墙钟区间（两次复跑） | 单意图延迟 p95 区间 | 吞吐（意图/秒） |
|---|---|---|---|---|
| 1 | 4 | 55.6–55.8 ms | 55.6–55.7 ms | 17.9–18.0 |
| 4 | 16 | 55.0–56.8 ms | 56.4 ms | 70–73 |
| 8 | 32 | 56.7–75.3 ms | 56.4–74.7 ms | 106–141 |
| 16 | 64 | 60.9–62.2 ms | 60.4–61.7 ms | 257–263 |
| 32 | 128 | 70.6–75.6 ms | 69.8–73.3 ms | 423–454 |

**读数**：
- 低并发（1–4）门面路径与内核直调几乎无差（~55ms）；**32 并发 / 128 分支点，门面墙钟 ~71–76ms（B 为 ~63–69ms），吞吐 ~423–454 意图/秒（B 为 ~467–511），门面附加约 5–10ms 墙钟、约 10–15% 吞吐损耗**。
- 8 并发一档两次复跑抖动明显（57ms / 75ms），属本机事件循环/连接池冷启动噪声，非稳定退化（相邻 4/16 档两次复跑均收敛）。
- 结论：**H2 门面（bearer + 路由 + JSON over loopback）在测到的并发范围内不是瓶颈**；真实跨网 RTT 与 TLS 会主导绝对延迟，需真机重标。

## 6. 场景 D：高并发取消传播（v0.2 新增）

执行 Agent 任务 settle 为非终态 **input-required**（挂起等待人工输入，`artifacts: []`）；待 K 个意图（每个 4 分支）全部挂起后，并发调用 `Orchestrator.cancelIntent`，其向每个非终态分支发 JSON-RPC `tasks/cancel`，mock farm 立即回 `canceled`。

| 挂起意图 K | 取消分支数 | 取消总墙钟区间（两次复跑） | 取消吞吐（cancels/秒） |
|---|---|---|---|
| 4 | 16 | 2.2–2.6 ms | 6,200–7,250 |
| 8 | 32 | 3.3–3.8 ms | 8,400–9,800 |
| 16 | 64 | 7.0–9.6 ms | 6,700–9,200 |
| 32 | 128 | 13.5–17.9 ms | 7,100–9,500 |

**读数**：
- **128 个挂起分支的取消信号在 ~14–18ms 内全部传播完成**，取消是即时的——不等待执行 Agent「思考」，墙钟随取消分支数近似线性、亚毫秒/分支级。
- 脚本断言每档每个非终态分支**恰好取消一次**（`canceled: true`），且 mock farm 跨四档**实收 240 个 `tasks/cancel`（=16+32+64+128），零丢失、零重复**；终态分支（completed/failed/canceled）按 F3 语义跳过。
- 取消吞吐在最高并发点略降（连接复用/事件循环竞争），但无超时、无失败；真实执行 Agent 的 cancel 处理速度与网络决定真机绝对值。
- 口径说明：此处取消的是**已 settle 的挂起（input-required）分支**，即 F3 `cancelIntent` 的设计场景。**对仍在 `working`、fanOut 尚未返回的运行中分支，v0.4 起已由 fan-out §7（Active work 115，commit `496d16b`）补上一等中断原语**：`DispatchRequest.signal?: AbortSignal` 透传到出站 A2A 流、orchestrator 以 `branchSignals` 持有每分支 `AbortController`、运行中分支 abort 后结算 `state:'canceled'` + `reason:'canceled by the operator'`、审计记 `branch-aborted`（不再误标 dispatch-failed）。场景 D 的取消吞吐在 §7 后同机对照无系统性变化（见状态行 v0.4 对照）。

## 7. 场景 E：并发闸门的代价（v0.3 新增）

对应 2026-09-25 落地的 E1.5 `maxConcurrentBranches` / `branchQueueLimit`。负载与场景 B 的最高档完全相同（**32 意图 × 4 分支 = 128 分支**），只改变闸门：无限制（内核默认）→ 32 → 16 → 8。

> **E 是 opt-in**：`node scripts/bench-capacity.mjs --cap`（`--cap 16` 只跑单档）。默认跑法不含 E——它给同一个进程内的 mock farm 追加 4×128 分支负载，会把 A/B 的看门狗顶到误触发（见下方"附带修正"）。

三次采样（M4/10C/node20，50ms think）：第 1 列来自 E 仍默认执行的早期跑法，第 2–3 列来自改为 `--cap` 显式开启后的两次独立全量复跑。**三者不可当作同分布样本**——第一列的进程里 A–E 全部串联，负载更高；列出只为展示散布幅度。

| cap | 墙钟 ms（三次） | 吞吐 分支/秒（三次） | 分支延迟 p95 ms | 实测 max in-flight | 实测 peak queue |
|---|---|---|---|---|---|
| 无限制 | 86.2 / 194.1 / 198.5 | 1485.7 / 659.6 / 644.7 | 85.9 / 193.6 / 197.1 | **128** | **0** |
| 32 | 249.8 / 349.7 / 354.5 | 512.4 / 366 / 361 | 248.6 / 346.1 / 347.7 | **32** | **96** |
| 16 | 450.6 / 629.4 / 540.5 | 284.1 / 203.4 / 236.8 | 448.6 / 605.5 / 536.5 | **16** | **112** |
| 8 | 857.5 / 994.7 / 1380.3 | 149.3 / 128.7 / 92.7 | 851.3 / 966.1 / 1363.2 | **8** | **120** |

**能拿来下结论的是不变量与比值，不是绝对值**：

1. **闸门语义逐次精确**：`max in-flight` 恰好等于配置的 cap（无限制时等于 128），`peak queue` 恰好等于 `128 − cap`（96/112/120），三次复跑零偏差；128 分支全部完成，`finished == 128`、失败/超时 0。等待线未设上限时不拒绝任何分支——与 `branchQueueLimit` 的语义一致。
2. **吞吐随 cap 近似线性**：`分支/秒 ≈ cap ÷ 单分支占用时间`。以 cap=32 的 ~366/秒 反推单分支占用 ≈ 87ms（think 50ms + 内核与 farm 开销），cap=16/8 实测值都落在这条线附近。这就是限流的定价：**上界砍一半，吞吐也砍一半**。
3. **尾延迟 ≈ 墙钟**：分支要排队等波次，最后一波的分支几乎要等整轮跑完，所以 p95 从 86ms（无限制）涨到 347/536/966–1363ms（cap 32/16/8）。给整个进程设闸，代价主要落在**尾部**而不是吞吐上。
4. **绝对值散布 ±2×**：无限制档墙钟 86→198ms、cap=8 档 857→1380ms。原因是 mock farm 与内核同进程抢事件循环，叠加本机背景负载。**因此本节不提供任何"每秒 N 意图"的承诺，只提供比值与不变量。**

### 附带修正：看门狗从 20×think 提到 40×think

`branchTimeoutMs` 原本是 `delayMs * 20`（50ms think → 1s）。加入 E 的满载跑法后，场景 A 在 width 64 出现**连续尾段 19 个分支同时超时**（`executor-45…63`），场景 B 在 128 分支档偶发单支超时——这是**单进程 farm 的事件循环停顿**撞上一个偏紧的看门狗，不是内核派发问题（实测 p95 只有 ~200ms，离 1s 很远，但停顿发生在同一时刻的一批分支上）。

处理：把该值收敛成显式常量 `BRANCH_WATCHDOG_MS = delayMs * 40` 并注释写明"它是防止分支永远挂着的看门狗，不是被测量的 SLO"——墙钟与百分位都来自采样，不来自这个数。**没有降低任何测量标准**：若真出现卡死，40× 一样会抓到；若是停顿误报，就不该由它决定成败。原始脚本 3/3、新脚本默认路径 5/5 + 2/2 均通过，无法把该抖动归因到本次改动，故按"看门狗过紧"记录而非"已修复的回归"。

## 9. 限制与后续

- mock 执行 Agent 不代表 LLM/网络；本文是**内核/门面/取消的开销下界 + 并发正确性证据**，不是容量承诺。
- 已测：扇出宽度（A）、并发意图（B）、H2 门面全链路吞吐（C）、高并发取消传播（D）、**并发闸门代价与不变量（E，v0.3）**、**等待线有限值下的拒绝率与等待时间（F，v0.7，见 §11）**。**仍未测**：SSE 长连接占用与连接数上限、内存占用随分支数曲线、**运行中（working）分支 AbortSignal 中断的专项容量场景**（§7 已落地该能力，但场景 D 压的是 input-required 挂起态的 `tasks/cancel`，尚未为"fanOut 未返回即 abort"单开一档）、**真实执行 Agent 的 per-executor 饱和曲线**（§11 只给出公式与触发条件）。
- **v0.3 复跑发现的散布要如实算作限制**：无限制档墙钟在 86–198ms 之间摆（±2×），cap=8 档 857–1380ms。同进程 farm 与本机背景负载所致。因此 v0.3 只用**比值 + 不变量**下结论，绝对吞吐/延迟一律标注为散布区间而非单点。
- **v0.4 补一条跨版本对照方法论**：墙钟绝对值**跨机器不可直接比较**（v0.3 与 v0.4 不同机，B@32 从 351–404 到 263–332 intents/秒的差异主要来自机器/负载，不是回归）。判断某次内核改动是否引入容量回归，必须用 `git worktree` 在**同一台机器、相邻时间窗、空闲状态**下对改动前后 commit 各跑 ≥2 次交替对照；与 `docker build` 等 CPU/IO 重活并发的跑次作废（v0.4 实测污染跑 B@16 掉到干净值的 ~64%）。结论只取**比值趋势 + 正确性不变量（零分支丢失、240 取消零丢失零重复）**，不根据单次绝对数下判断。
- 场景 D 的取消吞吐以 mock farm「立即 ack cancel」为前提；真实执行 Agent 可能异步取消，需在真机测量 cancel ack 延迟与最终一致性。
- 触发 deferred #9（≥3 真实执行 Agent 在线）后，应在真机用本脚本同款方法（替换为真实 taskUrl）重测，并把有界队列阈值、背压降级顺序写入本文下一版。

## 10. recall 微基准门禁（W2-1a 跟进，2026-10-31 并入门禁）

`scripts/bench-recall.mjs`（PR #172 交付的 RecallIndex 冷建/热同步/热查询/维度重建微基准）原先只有 `npm run bench:recall` 一个人跑入口，CI 零覆盖。本批把它的输出接进门禁，**并进既有 `bench-capacity` CI job**（取舍：build 才是重步骤且两闸完全相同，独立 job 要为一条命令多付一次 install+build；代价只是 job 名扩为 capacity + recall）。

- 脚本：`scripts/bench-recall-gate.mjs`（`npm run bench:recall:gate`）；基线文件 `recall-baseline.json`（与 `capacity-baseline.json` 同构，按指纹钉值）。
- **正确性硬闸在 bench-recall 自身**（冷建恰好 N 次 embed、热同步 0、热查询恰好 1、维度重建 N、已知查询命中——违规 throw 非零退出），门禁透传非零退出。
- **指纹**：`<platform>-<arch>-<cpus>-<node>-f<facts>-r<reps>-d<delay>`——比容量门禁多拼了 bench 形状参数，因为 CLI 可调 facts/reps/embed-delay，跨形状的数字不可比。
- **对比阈值：单一 +30% 硬红**（有意不做 bench-gate 的 ±15% 告警层：微基准重跑成本低，一层阈值保可读；更快永不红）。
- **噪声下限 5ms**：基线低于 5ms 的指标只打印不对比——local（纯 CPU）场景量的是亚毫秒级索引开销，±30% 落在抖动里不是回归；门禁实际由 simulated（模拟 hub 延迟）场景承载（默认形状下 gated 指标为 `simulated.coldBuild.p50` 与 `simulated.hotQuery.p50/p95`）。`hotSync.ms`（亚毫秒）与 `serialProjectionMs`（计算值非测量值）不参与。

## 11. 背压阈值标定（v0.7，2026-11-08，只出数据与建议）

### 11.1 现状：默认值是什么、依据在哪

| 配置 | 代码默认 | 现行证据 |
|---|---|---|
| `maxConcurrentBranches` | **未设置**（`state/boot.ts` 只在 env 显式给出时写入；`semaphore` 在无 cap 时不创建） | 无实测依据。§7 E 只证明"设了 cap 后语义正确、代价是等待与吞吐线性下降"，没有回答"应该设多少" |
| `branchQueueLimit` | **未设置**（`Semaphore` 默认 `Infinity`） | 同上。§9 明确把"有限等待线下的拒绝率与恢复"列为未测 |

结论：当前三个阈值都不是"根据数据定出来的默认值"，而是**保持关闭**。本节的建议同样不写入默认值，只作为启用时的取值依据。

### 11.2 方法与可观测性缺口

- 负载：`node scripts/bench-capacity.mjs --cap sweep --queue`。场景 E 仍是 **32 意图 × 4 分支 = 128 分支**，cap 无限制 → 32 → 16 → 8；新增场景 F 固定 cap=16，等待线 `branchQueueLimit` 扫 0 / 8 / 16 / 32 / 64 / 无限制。
- 观测：墙钟、分支/秒、单意图延迟 p50/p95、`in-flight` 峰值、队列深度采样峰值、**拒绝数**、**队列等待 p50/p95/max**。
- 缺口与补齐（`src/core/orchestrator/metrics.ts`，风格与既有指标一致：O(1) 写、快照时算百分位、窗口有界且自报 `trimmedQueueWaits`）：
  - `refused`：E 的等待线无限制，永远不会拒绝，`failed` 也恒为 0，因此"cap 满了以后是延迟还是拒绝"在原指标里不可见；F 需要它做正确性硬闸。
  - `queueWait`（p50/p95/max）：原指标只有 `finished` 延迟，无法把"排队等闸"与"执行本身"分开；标定 cap 时必须区分这两者。
  - `queuedPeak`：突发负载下"提交未启动"的峰值（含立即拿到槽位的分支），是突发规模信号，不等于等待线长度；等待线的效果看 `refused` 与 `queueWait`。
  - `diverted`：per-executor 自动改派的次数。本节 mock farm 没有 governor，所以该值为 0；补它是为了 #9 真机标定时能直接看到改派频率，而不是只从审计事件里数。
- 环境：Apple M4 / 10 CPU / darwin 27.2.0 arm64 / Node v22.23.4，mock farm 64 槽、单分支 think 50ms，同机单跑一轮（F 每档一轮）。与 §7 一样，**绝对值只作比值参考**，mock farm 与内核同进程抢事件循环。

### 11.4 拐点与建议

1. **cap 的拐点不是"128"，而是下游执行槽位数（本机 mock 为 64）**。cap ≥ 槽位数时，128 分支分两波完成，墙钟 ~70ms；cap=32 开始墙钟变成 ~3.3×（225ms），cap=16 ~6.6×，cap=8 ~12.4×，且 `单意图 p95 ≈ 墙钟 ≈ ceil(128/cap) × 单分支占用`。也就是说，**cap 一低于下游可并行槽位数，退化立刻开始，只是先体现在尾部延迟而不是吞吐**（吞吐仍近似 `cap / 单分支占用`，§7 已证）。
   - 建议（启用时）：`maxConcurrentBranches ≈` 已知的下游并发槽位数，或按 `目标 QPS × 最慢分支占用` 反推；不要显著低于槽位数，否则等于人为把突发串行化。mock 的 64 槽不能直接搬到真机——真机的"槽位"是最慢 Agent 的并发能力。
2. **queueLimit 是"延迟预算"而不是"容量参数"**。cap=16 下，queueLimit=0 时拒绝 87.5%，等待几乎为 0；queueLimit=16（1×cap）时等待 p95 ≈ 63ms（约 1.3× 单分支占用），仍拒绝 75%；queueLimit=64（4×cap）时等待 p95 226ms，拒绝降到 37.5%；无限制时等待 p95 390ms、零拒绝。等待随 `(cap+queue)/cap` 线性增长，与 Little 定律一致。
   - 建议（启用时）：先定可接受尾延迟，再取 `queueLimit ≈ cap × (可接受等待 / 单分支占用 − 1)`。以"等待不超过一个执行周期"为目标，`queueLimit = 1×cap`；能接受两个周期则 `2×cap`。**不要用无限制等待线做默认**：它在 8× 突发下会把 p95 从 60ms 拉到 390ms。
3. **`maxConcurrentPerExecutor` 本节给不出数值**。mock farm 是无状态并发处理器，不存在"单 Agent 越忙越慢"的饱和曲线；在这里测出的 per-executor 数字只会是内核开销，不是 Agent 容量。建议保留公式 `cap(v) ≈ 可接受单 Agent 排队延迟 / 单 Agent 服务时间`，并在 ≥3 真实 Agent（`design-backpressure.md` 的触发条件）在线后，用同一脚本的 F 形状按 per-executor 重测。`diverted` 指标已就绪，可直接观测改派频率。
4. **默认值保持关闭是本节的结论，不是遗漏**：没有真实 Agent 的饱和数据前，把 cap/queueLimit/cap(v) 写死会用一个 mock 数字替代真实容量判断。本次只补指标与数据，没有修改 `src` 业务默认、`boot` 默认或 compose/env 默认。
