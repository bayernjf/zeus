# Zeus 容量基线（E10.4，本机 mock 回环）

> 状态：**现行 v0.2（2026-09-24）**。对应 PRD E10.4「并发压测与容量基线」与 §6 成功指标。
> 复跑：`npm run build && npm run bench:capacity`（脚本 `scripts/bench-capacity.mjs`，零依赖；`--json` 出机器可读结果，`--delay-ms` / `--reps` / `--farm` 可调）。
>
> **v0.2 变更**：新增**场景 C（H2 门面全链路吞吐，真实回环 TCP + bearer + JSON）**与**场景 D（高并发取消传播，input-required 挂起态 → tasks/cancel）**；mock farm 同端点支持 JSON-RPC `tasks/cancel` 与可配终态。场景 A/B 测量逻辑未变，区间沿用 v0.1（v0.2 复跑因机器更空闲略好，未下调保守区间）。

## 1. 这是什么、不是什么

- **是**：Zeus 内核（Orchestrator → Dispatcher → undici fetch → 回环 HTTP；场景 C 额外经过 Fastify H2 门面）在**模拟封臣群**下的扇出/并发/门面/取消能力基线，量化 fan-out/merge/aggregate、HTTP 门面与取消传播自身开销，验证无分支丢失、无取消丢失、指标峰值可信。
- **不是**：真实封臣容量。mock 封臣固定 50ms「思考延迟」（场景 D 为 5ms）、无 LLM 推理、无跨网 RTT、无鉴权后端。真实场景的延迟与吞吐由封臣（LLM）和网络主导，本文数字只界定 **Zeus 自身不是瓶颈的区间**。
- 本机基准**负载敏感**，高负载点（64 扇出 / 32 并发意图）p95 波动较大；下列数字为 warmup 后独立复跑的区间，不是性能承诺。背压 / 有界队列仍为 deferred #9（触发条件：≥3 真实封臣压测）。

| 项 | 值 |

## 3. 场景 A：单意图扇出宽度

一个意图并行扇出 N 个封臣（每封臣 50ms）。理想并行时墙钟 ≈ 50ms（与 N 无关）；串行则为 50N ms。

| 扇出宽度 N | 墙钟 p50（两次复跑区间） | 墙钟 p95 区间 | 并行效率（50/p50） |
|---|---|---|---|
| 1 | 55–57 ms | 59–62 ms | 0.88–0.91 |
| 2 | 55–56 ms | 57–72 ms | 0.90–0.91 |
| 4 | 56–58 ms | 58–63 ms | 0.87–0.89 |
| 8 | 56–57 ms | 59–63 ms | 0.88–0.90 |
| 16 | 57–65 ms | 60–68 ms | 0.77–0.87 |
| 32 | 65–68 ms | 70–84 ms | 0.73–0.78 |
| 64 | 75–76 ms | 84–129 ms | 0.65–0.67 |

**读数**：
- 宽度 **1–16 墙钟稳定在 ~55–65ms**，与单封臣 50ms 几乎持平——并行扇出成立，内核 fan-out/合并/聚合在该量级附加开销约 **5–15ms**。
- **32–64** 回环连接与事件循环调度开销开始可见（p50 65–76ms，p95 尾延迟上升），但相对串行（64×50 = 3200ms）仍是数量级的优势。
- 结论：**单意图并行扇出 16 个封臣是本机可舒适支撑的量级**；32+ 可用但应配合 deferred #9 的有界队列在真机重新标定。

## 4. 场景 B：并发意图吞吐（内核直调）

C 个意图**同时**发起，每个意图扇出 4 个封臣（50ms），封臣在 64 个槽位间复用（与真实多租户复用一致）。

| 并发意图 C | 总分支数 | 总墙钟区间 | 单意图延迟 p95 区间 | 吞吐（意图/秒） | metrics 峰值在途 |
|---|---|---|---|---|---|
| 1 | 4 | 54–63 ms | 54–63 ms | 16–19 | 4 |
| 4 | 16 | 59–62 ms | 57–61 ms | 65–68 | 16 |
| 8 | 32 | 63–64 ms | 61–62 ms | 125–127 | 32 |
| 16 | 64 | 72–82 ms | 67–75 ms | 195–222 | 64 |
| 32 | 128 | 79–91 ms | 73–78 ms | 351–404 | 128 |

**读数**：
- **128 个分支同时在途，全部 completed、零分支丢失**（每点 `finishedBranches === totalBranches`）；`ConcurrencyMetrics.maxInFlight` 准确捕获 4/16/32/64/128 峰值。
- 32 并发意图下单意图 P95 仍在 **~80ms**（仅比单意图多 ~20–25ms），mock 回环吞吐约 **350–400 意图/秒**——该数字主要被人为 50ms think 决定，真实场景会低得多，此处仅证明内核调度在 128 并发分支下不构成瓶颈。
- 当前为无界 `Promise.all`（无背压）；128 并发在 mock 下健康，**真实封臣的连接/限流约束必须在 deferred #9 落地有界队列后，于真机重新压测**。

## 5. 场景 C：H2 驱动门面全链路吞吐（v0.2 新增）

与场景 B 同负载，但意图从**真实 HTTP 门面**进入：`POST /api/intents`（bearer 鉴权 → Fastify 路由 → JSON 解析 → 同一 Orchestrator/Dispatcher → mock farm → JSON 序列化），走 127.0.0.1 TCP。与 B 的差值即**门面 + 鉴权 + JSON 往返开销**。

| 并发意图 C | 总分支数 | 总墙钟区间（两次复跑） | 单意图延迟 p95 区间 | 吞吐（意图/秒） |
|---|---|---|---|---|
| 1 | 4 | 55.6–55.8 ms | 55.6–55.7 ms | 17.9–18.0 |
| 4 | 16 | 55.0–56.8 ms | 56.4 ms | 70–73 |
| 8 | 32 | 56.7–75.3 ms | 56.4–74.7 ms | 106–141 |
| 16 | 64 | 60.9–62.2 ms | 60.4–61.7 ms | 257–263 |
| 32 | 128 | 70.6–75.6 ms | 69.8–73.3 ms | 423–454 |

**读数**：
- 低并发（1–4）门面路径与内核直调几乎无差（~55ms）；**32 并发 / 128 分支点，门面墙钟 ~71–76ms（B 为 ~63–69ms），吞吐 ~423–454 意图/秒（B 为 ~467–511），门面附加约 5–10ms 墙钟、约 10–15% 吞吐损耗**。
- 8 并发一档两次复跑抖动明显（57ms / 75ms），属本机事件循环/连接池冷启动噪声，非稳定退化（相邻 4/16 档两次复跑均收敛）。
- 结论：**H2 门面（bearer + 路由 + JSON over loopback）在测到的并发范围内不是瓶颈**；真实跨网 RTT 与 TLS 会主导绝对延迟，需真机重标。

## 6. 场景 D：高并发取消传播（v0.2 新增）

封臣任务 settle 为非终态 **input-required**（挂起等待人工输入，`artifacts: []`）；待 K 个意图（每个 4 分支）全部挂起后，并发调用 `Orchestrator.cancelIntent`，其向每个非终态分支发 JSON-RPC `tasks/cancel`，mock farm 立即回 `canceled`。

| 挂起意图 K | 取消分支数 | 取消总墙钟区间（两次复跑） | 取消吞吐（cancels/秒） |
|---|---|---|---|
| 4 | 16 | 2.2–2.6 ms | 6,200–7,250 |
| 8 | 32 | 3.3–3.8 ms | 8,400–9,800 |
| 16 | 64 | 7.0–9.6 ms | 6,700–9,200 |
| 32 | 128 | 13.5–17.9 ms | 7,100–9,500 |

**读数**：
- **128 个挂起分支的取消信号在 ~14–18ms 内全部传播完成**，取消是即时的——不等待封臣「思考」，墙钟随取消分支数近似线性、亚毫秒/分支级。
- 脚本断言每档每个非终态分支**恰好取消一次**（`canceled: true`），且 mock farm 跨四档**实收 240 个 `tasks/cancel`（=16+32+64+128），零丢失、零重复**；终态分支（completed/failed/canceled）按 F3 语义跳过。
- 取消吞吐在最高并发点略降（连接复用/事件循环竞争），但无超时、无失败；真实封臣的 cancel 处理速度与网络决定真机绝对值。
- 口径说明：此处取消的是**已 settle 的挂起（input-required）分支**，即 F3 `cancelIntent` 的设计场景；对仍在 `working`、fanOut 尚未返回的分支，编排层当前不提供按 intentId 的一等取消（intent 结果在 fanOut 完成后才登记），该能力属后续演进项，不在本基线范围。

## 8. 限制与后续

- mock 封臣不代表 LLM/网络；本文是**内核/门面/取消的开销下界 + 并发正确性证据**，不是容量承诺。
- 已测（v0.2）：扇出宽度、并发意图、H2 门面全链路吞吐、高并发取消传播。**仍未测**：SSE 长连接占用与连接数上限、内存占用随分支数曲线、对仍在 working 的进行中意图的取消、背压/有界队列。
- 场景 D 的取消吞吐以 mock farm「立即 ack cancel」为前提；真实封臣可能异步取消，需在真机测量 cancel ack 延迟与最终一致性。
- 触发 deferred #9（≥3 真实封臣在线）后，应在真机用本脚本同款方法（替换为真实 taskUrl）重测，并把有界队列阈值、背压降级顺序写入本文下一版。
