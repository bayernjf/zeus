# Zeus 容量基线（E10.4，本机 mock 回环）

> 状态：**现行 v0.1（2026-09-24）**。对应 PRD E10.4「并发压测与容量基线」与 §6 成功指标。
> 复跑：`npm run build && npm run bench:capacity`（脚本 `scripts/bench-capacity.mjs`，零依赖；`--json` 出机器可读结果，`--delay-ms` / `--reps` / `--farm` 可调）。

## 1. 这是什么、不是什么

- **是**：Zeus 内核（Orchestrator → Dispatcher → undici fetch → 回环 HTTP）在**模拟封臣群**下的扇出/并发能力基线，量化 fan-out/merge/aggregate 自身开销与 Node 客户端并发上限，验证无分支丢失、指标峰值可信。
- **不是**：真实封臣容量。mock 封臣固定 50ms「思考延迟」、无 LLM 推理、无跨网 RTT、无鉴权后端。真实场景的延迟与吞吐由封臣（LLM）和网络主导，本文数字只界定 **Zeus 自身不是瓶颈的区间**。
- 本机基准**负载敏感**，高负载点（64 扇出 / 32 并发意图）p95 波动较大；下列数字为 warmup 后两次独立复跑的区间，不是性能承诺。背压 / 有界队列仍为 deferred #9（触发条件：≥3 真实封臣压测）。

| 项 | 值 |

## 3. 场景 A：单意图扇出宽度

一个意图并行扇出 N 个封臣（每封臣 50ms）。理想并行时墙钟 ≈ 50ms（与 N 无关）；串行则为 50N ms。

| 扇出宽度 N | 墙钟 p50（两次复跑区间） | 墙钟 p95 区间 | 并行效率（50/p50） |
|---|---|---|---|
| 1 | 55–57 ms | 59–62 ms | 0.88–0.91 |
| 2 | 55–56 ms | 57–72 ms | 0.90–0.91 |
| 4 | 56–58 ms | 58–63 ms | 0.87–0.89 |
| 8 | 56–57 ms | 59–63 ms | 0.88–0.90 |
| 16 | 57–65 ms | 60–68 ms | 0.77–0.87 |
| 32 | 65–68 ms | 70–84 ms | 0.73–0.78 |
| 64 | 75–76 ms | 84–129 ms | 0.65–0.67 |

**读数**：
- 宽度 **1–16 墙钟稳定在 ~55–65ms**，与单封臣 50ms 几乎持平——并行扇出成立，内核 fan-out/合并/聚合在该量级附加开销约 **5–15ms**。
- **32–64** 回环连接与事件循环调度开销开始可见（p50 65–76ms，p95 尾延迟上升），但相对串行（64×50 = 3200ms）仍是数量级的优势。
- 结论：**单意图并行扇出 16 个封臣是本机可舒适支撑的量级**；32+ 可用但应配合 deferred #9 的有界队列在真机重新标定。

## 4. 场景 B：并发意图吞吐

C 个意图**同时**发起，每个意图扇出 4 个封臣（50ms），封臣在 64 个槽位间复用（与真实多租户复用一致）。

| 并发意图 C | 总分支数 | 总墙钟区间 | 单意图延迟 p95 区间 | 吞吐（意图/秒） | metrics 峰值在途 |
|---|---|---|---|---|---|
| 1 | 4 | 54–63 ms | 54–63 ms | 16–19 | 4 |
| 4 | 16 | 59–62 ms | 57–61 ms | 65–68 | 16 |
| 8 | 32 | 63–64 ms | 61–62 ms | 125–127 | 32 |
| 16 | 64 | 72–82 ms | 67–75 ms | 195–222 | 64 |
| 32 | 128 | 79–91 ms | 73–78 ms | 351–404 | 128 |

**读数**：
- **128 个分支同时在途，全部 completed、零分支丢失**（每点 `finishedBranches === totalBranches`）；`ConcurrencyMetrics.maxInFlight` 准确捕获 4/16/32/64/128 峰值。
- 32 并发意图下单意图 P95 仍在 **~80ms**（仅比单意图多 ~20–25ms），mock 回环吞吐约 **350–400 意图/秒**——该数字主要被人为 50ms think 决定，真实场景会低得多，此处仅证明内核调度在 128 并发分支下不构成瓶颈。
- 当前为无界 `Promise.all`（无背压）；128 并发在 mock 下健康，**真实封臣的连接/限流约束必须在 deferred #9 落地有界队列后，于真机重新压测**。

## 5. 对 PRD 容量目标的初步回答（待真机修正）

| PRD §6 指标 | mock 本机基线（2026-09-24） | 真机目标 |
|---|---|---|
| 单意图可并发 Agent 数 | 舒适区 ≤16（p95 <70ms）；32–64 可用、尾延迟上升 | 待 ≥3 真实封臣 + deferred #9 标定 |
| 平台同时在途任务数 | 验证到 128 在途分支零丢失、P95 ~80ms（mock） | 待真机；有界队列阈值据此设定 |
| P95 决策延迟 | 内核附加开销 ~5–15ms（50ms mock think 下） | 真实值 ≈ 最慢封臣 LLM 延迟 + 该开销 |
| 冲突正确识别率 | 不由压测覆盖（见 E1.4/E6.2 单测） | 真机语料集评估 |

## 6. 限制与后续

- mock 封臣不代表 LLM/网络；本文是**内核开销下界 + 并发正确性证据**，不是容量承诺。
- 未测：取消传播在高并发下的行为、SSE 长连接占用、HTTP 门面（H2）全链路吞吐、内存占用随分支数曲线——需要时扩展脚本场景。
- 触发 deferred #9（≥3 真实封臣在线）后，应在真机用本脚本同款方法（替换为真实 taskUrl）重测，并把有界队列阈值、背压降级顺序写入本文 v0.2。
