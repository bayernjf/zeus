# Zeus 产品画像（Product Portrait）

> 一份可迭代的活文档。产品的每一次定位演进都记录在文末「演进日志」中。
> 最新版本：v0.4（2026-09-22，核心定位修正为高并发多 Agent 协同决策）

---

## 0. 一句话定位

**Zeus 是一个高并发、多 Agent 协同决策的平台，以用户数据目录为底座：一个意图可扇出多个 Agent 并行执行、聚合为可追溯的决策。对个人，是记忆的避风港与可传承的藏宝图；对企业，是一个即插即用、伴随企业成长的"虚拟部门"。**

## 1. 愿景与使命

- **愿景**：让大模型（但不局限于 LLM）成为人类坚强的后盾——人是主权者与驾驶员，Agent 是得力干将与后盾。
- **使命**：
  1. 让数据主权永远在用户手中：给一个目录，产品即插即用；拿走目录，产品可以被替换。
  2. 让能力可以被组建、加固、传承：招兵买马、导师带教、技能沉淀。
  3. 让用户只面对一扇门：Zeus 统一调度背后的一切产品与 Agent。

## 2. 设计哲学（Constitution）

### 2.1 用户是底座，产品是插件（反向锁定）
- 用户指定一个或多个**数据目录**，这是产品汲取数据的唯一（或之一）来源。
- 目录即数据库：先连接，后使用；产品通过接口暴露数据，供内部 Agent 与外部系统使用。
- 备份是第一公民：产品有责任提供备份方案与恢复路径。
- 归属感来源于"你随时可以走，但你选择留下"，而非锁定。

### 2.2 藏宝图即恢复协议（诗性与工程同构）
- 用户资产功能记录的不是具体数据，而是抽象的**藏宝图**：一份加密的数据清单（manifest）+ 恢复指引（recovery protocol）。
- 用户手持藏宝图，按图索骥即可找到宝藏；Zeus 的责任是替用户保管藏宝图的备份、提供备份思路。
- 日记 = 记忆的备份；传承 = 带授权与触发条件的恢复协议。
- 数据必须区分**个人数据域**与**企业数据域**，边界清晰，不可混洄。

### 2.3 立国三纲：MCP、Skill、A2A
| 协议 | 本质 | 说明 |
|---|---|---|
| **MCP** | 连接世界 | 集成任何允许集成的系统，作为数据与工具来源 |
| **Skill** | 成长 | 技能可加固、可传授、可沉淀为个人/部门资产 |
| **A2A** | 社会组织 | Agent 之间（含外部 Agent）可互操作、可委托、可协作 |

三纲不是功能清单，而是所有能力接入的强制姿势。

### 2.4 同一引擎，两套治理
个人版与企业版共用全部原语，差异只在治理模型：单一主权 + 继承 vs 多租户 + 编制 + 审计 + 上岗。

### 2.5 三层同构，断裂即失败（核心理解）
Zeus 不是又一个 AI 助手，而是一次**信任结构的反向收编**：把 AI 从住在云端、锁着用户数据的租客，变成驻扎在用户目录里、向用户效忠的家臣团队。它由三层叠加而成，三层必须一一对应、同构：

1. **底座层（信任翻转）**：目录即数据库，产品是插件。拔掉目录，产品什么都不是。数据主权、备份第一公民、只经接口碰数据——这一层决定它是可插拔的，而非新围城。
2. **叙事层（情绪价值的真实来源）**：藏宝图、日记、传承不是文案贴花，而是真实工程原语的叙事外壳（加密 manifest + 恢复协议 + 授权触发）。归属感由"记忆真的丢不了、真能找回、真能交给想交的人"这个事实长出来；提效只是理由，归属感才是留存。
3. **组织层（同一内核长成虚拟部门）**：企业里，人是驾驶员与监督员而非被替代者；封臣联邦的政治结构（星型拓扑、宣誓效忠、可吊销、名册可验）与技术结构是同一套设计。

**生命线风险**：叙事与工程的同构一旦断裂，产品会塌成两边都不讨好——要么是备份工具讲情怀故事，要么是编排平台贴情绪标签。因此"藏宝图必须真能恢复宝藏"这类约束是产品生命线，不是技术细节；任何诗性概念找不到对应工程原语时，不得进入产品。

## 3. 核心概念词汇表（Glossary）

| 概念 | 含义 |
|---|---|
| **Realm 数据域** | 用户指定的一个目录及其接口，分 Personal Realm / Enterprise Realm |
| **Vault 宝库** | 数据域内被纳管、有备份策略的数据集合 |
| **Map 藏宝图** | 加密的数据清单 + 恢复指引，不存宝藏，只存"怎么找到宝藏" |
| **Diary 日记** | 记忆的叙事化备份，提供情绪价值与可回溯性 |
| **Agent 成员** | 可被招募的执行单元，有角色、能力边界与上岗状态 |
| **Mentor 导师** | 负责带教的 Agent：传递企业文化、业务上下文、岗位职责 |
| **Team 编制** | Agent 团队的组织结构，支持"招兵买马"与 A2A 协作 |
| **Skill 技能** | 可安装、可加固、可传授的能力包 |
| **Connector 连接器** | 基于 MCP 的外部系统接入 |
| **Delegation 委托** | 基于 A2A 的任务派发与战报回流，含外部 Agent |
| **Inheritance 传承** | 藏宝图/数据域按预设授权继承给后代（后期功能，含法律与密钥托管设计） |
| **Driver 驾驶员** | 人类员工的默认角色：监督、掌舵、拍板，而非手工执行 |

## 4. 用户画像

### 4.1 个人用户
- **诉求**：工作提效（实用）+ 记忆与数据的安全感 + 情绪价值 + 可传承。
- **场景**：一个目录接入工作与生活数据；组建自己的 Agent 班子；写日记、备藏宝图；必要时把图传给后代。
- **情感承诺**：被记住、被保护、不被绑架。

### 4.2 企业用户
- **诉求**：新员工上岗即用；业务流程由 A2A 系统承接，员工做驾驶员/监督员；知识与人不随员工离职流失；合规与审计。
- **场景**：Mentor Agent 向新员工讲解企业文化、具体业务、负责事项；员工作为 Agent 团队的监督者；Zeus 作为一个"部门"存在并对业务结果负责。
- **情感承诺（面向员工）**：港湾——有导师、有归属、有安全感。
- **商业承诺（面向采购方）**：虚拟部门、人效提升、知识留存、权限审计。

### 4.3 重合与差异
| 维度 | 个人 | 企业 |
|---|---|---|
| 数据域 | 单一主权 | 多租户，组织/部门/个人分级 |
| 核心叙事 | 避风港、藏宝图、传承 | 虚拟部门、导师、港湾 |
| Agent 关系 | 私人班子 | 编制 + 上下级 + 人类监督 |
| 备份 | 个人备份策略 | 组织级容灾 + 权限继承 |
| 上手成本 | 自己摸索亦可 | 必须上岗即用 |
| 合规 | 隐私 | 审计、权限、数据不出域 |

个人数据域与企业数据域可在同一员工处共存，但默认有**数据二极管**：未经明确授权，个人域不进企业，企业域不离组织。

## 5. 产品架构（分层）

```
┌─────────────────────────────────────────────┐
│  叙事层  藏宝图 · 日记 · 导师 · 港湾 · 传承     │  情绪价值 / 归属感
├─────────────────────────────────────────────┤
│  协作层  编制(Team) · 委托(A2A) · 监督台        │  多 Agent 社会
├─────────────────────────────────────────────┤
│  能力层  Skill 技能包 · Mentor 带教 · Agent 注册 │  成长
├─────────────────────────────────────────────┤
│  连接层  MCP 连接器 · 外部 Agent(A2A) · 封臣产品 │  连接世界
├─────────────────────────────────────────────┤
│  数据层  Realm 目录 · Vault 宝库 · Map 清单 · 备份│  主权底座
└─────────────────────────────────────────────┘
```

## 6. 对外接口与协议要求

1. **数据接口**：Realm 接入后必须暴露标准读写/检索接口；一切 Agent 先连接数据层，再谈能力。
2. **MCP**：任何外部系统通过 MCP 暴露 resources/tools/prompts；企业侧要求可审计、可断权。
3. **Skill**：技能包声明输入、权限、依赖；可安装、可版本化、可由 Mentor 传授给新 Agent/新员工。
4. **A2A**：
   - 每个 Agent（含外部、含封臣产品）提供 **Agent Card**：身份、能力、端点、认证方式。
   - 支持任务受理（intake）、状态回传、战报回流（report-back）、升级人类（escalation）。
   - 人类始终保留中断、改道、拍板的最高权限。

## 7. 产品矩阵联邦：分封，而非吞并

现有矩阵——**agent-world、job-agent、agent-dev、pr-helper、atlas、loom**，以及展示站 **bayjf**——各自保持独立仓库、独立部署与独立人格，通过统一的**封臣协议（Vassal Protocol）**向 Zeus 负责：

1. **注册**：产品暴露 Agent Card，登记能力域与端点。
2. **受理**：Zeus 通过 A2A/MCP 向其派发任务，产品变为 headless 能力。
3. **回流**：执行状态与结果以战报形式回到 Zeus，由 Zeus 统一对用户呈现。
4. **用户视角**：只面对 Zeus，不面对产品矩阵；矩阵产品成为 Zeus "增强"出来的能力。
5. **bayjf 的新角色**：从产品陈列馆升级为 Zeus 的「封神榜」——可招募的干将名册与能力说明。

**落地顺序**：pr-helper 作为第一个封臣，打磨封臣协议 → 推广至 loom/atlas → 全矩阵纳入。

## 8. 情绪价值设计原则

- 安全感来自**可备份、可迁移、可继承**，而非口号。
- 藏宝图、日记使用叙事化语言，但每一项都对应真实可执行的恢复动作。
- 企业版内部对员工讲"港湾与导师"，对外对采购方讲"部门与 ROI"——同一引擎，两套包装。
- 传承（Inheritance）涉及法律、密钥托管与触发机制，后期单独立项；前期先用藏宝图备份验证情感闭环。

## 9. 初步演进路线（待细化）

- **P0 楔子**：目录接入 + 数据接口 + 备份；单 Agent 组队；pr-helper 作为首个封臣跑通封臣协议。
- **P1 协作**：A2A 编制与监督台；Skill 安装/加固；MCP 连接器市场雏形；2–3 个矩阵产品纳入。
- **P2 双态**：企业 Realm 多租户 + Mentor 带教 + 上岗流程；个人藏宝图与日记；bayjf 封神榜。
- **P3 传承**：继承协议、密钥托管、合规与法律框架；全矩阵联邦完成。

## 10. 开放问题（Open Questions）

1. 封臣协议是直接复用 A2A 标准的超集，还是自定义最小协议？
2. 藏宝图的加密与托管：纯本地密钥 vs 可恢复托管，如何取舍？
3. 企业版的计费单元：按"部门/编制"还是按席位？
4. 个人与企业数据域共存时，授权粒度与审计呈现如何设计？
5. 外部 Agent 接入的信任分级与沙箱边界？
