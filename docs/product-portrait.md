# Zeus 产品画像（Product Portrait）

## 0. 一句话定位

**Zeus 是一个高并发、多 Agent 协同决策的平台，以用户自己的数据目录为数据基础层：一个任务意图可并行分发给多个 Agent 执行，并聚合为可追溯的决策。对个人，它提供可验证的数据保全与跨代人移交；对企业，它提供一支可按需组建、可审计、可对业务结果负责的 Agent 团队。**

## 1. 愿景与使命

- **愿景**：让大模型（但不局限于 LLM）成为可靠的执行支撑——人保留主权与决策权，Agent 承担执行。
- **使命**：
  1. 数据主权永远在用户手中：给一个目录，产品即可使用；拿走目录，产品可被替换。
  2. 能力可被组织、约束与移交：注册接入、权限收窄、能力认证、经验沉淀。
  3. 用户只面对一个入口：Zeus 统一调度背后的一切产品与 Agent。

## 2. 设计约束（Constitution）

### 2.1 用户目录是基础层，产品是可插拔扩展（反向锁定）

- 用户指定一个或多个**数据目录**，这是产品获取数据的唯一（或其中之一）来源。
- 目录即数据库：先连接，后使用；产品通过接口暴露数据，供内部 Agent 与外部系统使用。
- **备份与恢复是一等能力**：产品有责任提供备份方案与恢复路径。
- 用户留存来自"你随时可以走，但你选择留下"，而不是锁定。

### 2.2 备份清单就是恢复协议

- 产品对用户资产功能的记录不是数据本身，而是**一份加密的数据清单（manifest）+ 一份可执行的恢复协议**：清单只存条目引用与指纹，不存正文。
- 用户持有清单即可定位并找回自己的数据；产品的责任是保证"按清单真能恢复"，并托管清单的副本与备份策略。
- 派生概念一律成对：**叙事日志 = 记忆的可读备份**；**移交与继承 = 带授权与触发条件的恢复协议**。
- 数据必须区分**个人数据域**与**企业数据域**，边界清晰，不可混用。

> 这一节的命名是产品有意选择的面向用户的表述层（见 §8）。约束是**双向的**：任何面向用户的表述都必须有 1:1 对应的可执行工程原语；找不到对应原语的表述，不得进入产品与文档。

### 2.3 三条能力接入通道：MCP、Skill、A2A

| 协议 | 作用 | 说明 |
|---|---|---|
| **MCP** | 连接外部系统 | 集成任何允许集成的系统，作为数据与工具来源 |
| **Skill** | 能力与权限声明 | 技能可声明输入/权限/依赖，可版本化、可收窄、可认证 |
| **A2A** | 跨 Agent 协作 | Agent 之间（含外部 Agent）可互操作、可委托、可协作 |

三条通道不是功能清单，而是**所有能力接入的强制形态**：不允许私有旁路。

### 2.4 同一引擎，两套治理

个人版与企业版共用全部原语，差异只在治理模型：单一所有者 + 移交 vs 多租户 + 组织结构 + 审计 + 任职资格校验。

### 2.5 三层必须一一对应，断裂即失败（核心理解）

Zeus 不是又一个 AI 助手，而是一次**部署形态与信任关系的翻转**：把模型从"住在云端、持有用户数据的服务方"变成"运行在用户目录内、对用户负责的执行方"。它由三层叠加而成，三层必须一一对应：

1. **数据层（信任翻转）**：目录即数据库，产品是可插拔扩展。拔掉目录，产品不持有任何东西。数据主权、备份一等能力、只经接口访问数据——这一层决定它是可替换的，而不是新的锁定。
2. **表述层（用户可感知的价值）**：备份清单、叙事日志、移交协议这些面向用户的说法，每一项都是真实工程原语的对外表述（加密 manifest + 恢复协议 + 授权触发条件），不是文案修饰。用户的安全感来自"数据确实丢不了、确实能找回、确实能交给指定的人"这一事实；效率提升只是理由，这一条才是留存。
3. **组织层（同一套运行时支撑部门结构）**：在企业里，人是决策与监督者而非被替代者；外部 Agent 生态的治理结构（集中式拓扑、显式归属声明、可吊销、可验签的目录快照）与其技术结构是同一套设计，不是两套。

**风险所在**：表述与工程的对应一旦断裂，产品两头不讨好——要么是备份工具在讲情怀，要么是编排平台贴了情绪标签。所以"备份清单必须真能恢复数据"这类约束是产品生命线，不是技术细节。

## 3. 概念词汇表（Glossary）

| 概念 | 含义 |
|---|---|
| **Realm 数据域** | 用户指定的一个目录及其接口，分 Personal Realm / Enterprise Realm |
| **Vault 备份域** | 数据域内被纳管、有备份策略的数据集合 |
| **Map 备份清单** | 加密的数据清单 + 恢复指引；只存条目引用与指纹，不存数据正文 |
| **Diary 叙事日志** | 记忆事件的按天可读记录，用于回溯与对外呈现 |
| **Agent 执行单元** | 可注册、可派发的执行方，有角色、能力边界与任职资格状态 |
| **Mentorship 能力认证** | 由已具备能力的 Agent 对学习方逐项评估，通过后才授予"该能力提供者"身份 |
| **Org 组织结构** | 部门、职位、归属与责任链；支持按需组建与跨 Agent 协作 |
| **Skill 技能** | 可安装、可版本化、可权限收窄的能力声明 |
| **Connector 连接器** | 基于 MCP 的外部系统接入 |
| **Delegation 任务委派** | 基于 A2A 的任务派发与结果回传，含外部 Agent |
| **Inheritance 移交与继承** | 数据域/备份清单按预设授权移交给指定对象（后期功能，含法律与密钥托管设计） |
| **Operator 操作者** | 人类员工的角色：监督、介入、给出最终裁决，而非手工执行 |

> 代码、环境变量、HTTP 路径与协议字段里保留了一批历史标识符（`vassal` / `fealty` / `roster` / `vault` / `realm` / `kernel` / `commission` / `mentor` / `diary` / `noul` 等）。它们是接口的一部分，逐个含义见 [terminology.md](terminology.md)。

## 4. 用户画像

### 4.1 个人用户

- **诉求**：工作提效 + 数据与记忆的安全感 + 可移交。
- **场景**：一个目录接入工作与生活数据；组建自己的 Agent 团队；生成叙事日志与备份清单；必要时按预设授权把数据移交给他人的。
- **承诺**：数据被完整保存、可恢复、不被锁定。

### 4.2 企业用户

- **诉求**：新员工就任即可用；业务流程由 A2A 系统承接，员工做监督与决策者；知识与能力不随人员流动流失；合规与审计。
- **场景**：已认证的 Agent 向新员工讲解企业文化、具体业务与职责范围；员工作为 Agent 团队的监督者；Zeus 作为一个部门存在并对业务结果负责。
- **对员工的承诺**：有支撑、有归属、有安全感。
- **对采购方的承诺**：可按需组建的团队、人效提升、知识留存、权限审计。

### 4.3 重合与差异

| 维度 | 个人 | 企业 |
|---|---|---|
| 数据域 | 单一所有者 | 多租户，组织/部门/个人分级 |
| 主要价值 | 数据保全、可恢复、可移交 | 组织化的 Agent 团队、责任链 |
| Agent 关系 | 自有团队 | 组织结构 + 上下级 + 人类监督 |
| 备份 | 个人备份策略 | 组织级容灾 + 权限继承 |
| 上手成本 | 自己摸索亦可 | 就任即可用 |
| 合规 | 隐私 | 审计、权限、数据不出域 |

个人数据域与企业数据域可在同一员工处共存，但默认是**单向隔离（data diode）**：未经明确授权，个人域不进企业，企业域不离组织。

## 5. 产品架构（分层）

```
┌──────────────────────────────────────────────────┐
│  表述层  备份清单 · 叙事日志 · 能力认证 · 移交      │  用户可感知的价值
├──────────────────────────────────────────────────┤
│  协作层  组织结构 · 任务委派(A2A) · 人工处理队列    │  多 Agent 协同
├──────────────────────────────────────────────────┤
│  能力层  Skill 声明 · 能力认证 · Agent 注册         │  能力成长与约束
├──────────────────────────────────────────────────┤
│  连接层  MCP 连接器 · 外部 Agent(A2A) · 矩阵产品    │  外部系统集成
├──────────────────────────────────────────────────┤
│  数据层  Realm 目录 · Vault 备份域 · Map 清单 · 备份│  数据主权
└──────────────────────────────────────────────────┘
```

## 6. 对外接口与协议要求

1. **数据接口**：数据域接入后必须暴露标准读写/检索接口；一切 Agent 先连接数据层，再谈能力。
2. **MCP**：任何外部系统通过 MCP 暴露 resources / tools / prompts；企业侧要求可审计、可断权。
3. **Skill**：技能声明输入、权限、依赖；可安装、可版本化、可由已认证 Agent 传给新 Agent / 新员工。
4. **A2A**：
   - 每个 Agent（含外部、含矩阵产品）提供 **Agent Card**：身份、能力、端点、认证方式。
   - 支持任务受理（intake）、状态回传、结果回传（report-back）、升级人工（escalation）。
   - 人类始终保留中断、改道、给出最终裁决的最高权限。

## 7. 矩阵产品生态：联邦接入，不合并代码库

现有矩阵——**agent-world、job-agent、agent-dev、pr-helper、atlas、loom**，以及展示站 **bayjf**——各自保持独立仓库、独立部署与独立定位，通过统一的**执行 Agent 协议（Vassal Protocol）**向 Zeus 负责：

1. **注册**：产品暴露 Agent Card，登记能力域与端点。
2. **受理**：Zeus 通过 A2A / MCP 向其派发任务，产品成为无头（headless）能力。
3. **回传**：执行状态与结果回到 Zeus，由 Zeus 统一对用户呈现。
4. **用户视角**：只面对 Zeus，不面对产品矩阵；矩阵产品成为 Zeus 扩展出来的能力。
5. **bayjf 的新角色**：从产品陈列站升级为**对外发布的已签名能力目录**——消费签名目录快照、客户端验签后公开展示可招募的执行单元。

**落地顺序**：pr-helper 作为第一个接入的执行 Agent，用于打磨协议 → 推广至 loom / atlas → 全矩阵纳入。

### 7.1 执行 Agent 接入波次表

> 波次是**接入打磨顺序**，不是重要性排序；每个项目在册地位平等。能力域一律以其登记的 Agent Card 为准，本表不预设各产品具体职责。每一波的前置条件满足才开工，不自动跳波。

| 波次 | 项目 | 角色 | 前置条件 | 出口标准 |
|---|---|---|---|---|
| **W1 首个执行 Agent** | **pr-helper** | 第一个接入方，用它打磨协议全链路（Card 注册 / send+SSE / 结果回传 / 升级 / 吊销 / 审计） | 协议所需库内能力就绪 | 真机（Vercel 部署）上受 Zeus 调度，全链路闭环；协议在此定型 |
| **W2 协议推广** | **loom**、**atlas** | 验证协议对**已有 A2A 实现**的复用与对账（loom 后端已有 `core/a2a/`，适合核对超集不破坏标准） | W1 协议定型 | loom 与 Zeus 联调通过；atlas 同波接入；标准客户端超集守护验收 |
| **W3 全矩阵** | **agent-world**、**job-agent**、**agent-dev** | 生态收口：剩余矩阵产品按 W1 定型协议登记为无头能力 | W2 跑通，协议与接入流程可复制 | 六个矩阵产品全部在册、可调度、可吊销；用户只面对 Zeus 一个入口 |
| **配套（非执行 Agent）** | **bayjf** | 展示站升级为对外签名目录：消费快照、客户端验签后公开展示 | 签名链 v1（E4.9）落地 | 只消费验签快照、不直接信任源；与内部目录隔离 |

**推进规则**：

- 同一波内可并行接入；**跨波必须等前一波出口标准达成**（W1 不定型不推广，避免协议在多个产品上返工）。
- 每个执行 Agent 接入前都要过：归属声明与版本协商 → Card 能力登记 → 最小权限边界 → 单向数据隔离；任一不过不派发。
- 仓库外关口（真机部署、联调环境）须负责人点工/授权，不在库内自动开工。
- W3 各项目的实际波次位置如与排期冲突，可在 W2 收尾时按就绪度微调，但 W1 = pr-helper 不变。

## 8. 面向用户的表述原则

- 安全感来自**可备份、可迁移、可移交**这一可验证事实，不来自口号。
- 产品面向用户可以使用易懂的说法（如"备份清单""叙事日志"），但**每一句都必须对应一个真实可执行的恢复动作**；对外技术文档与本仓库内部文档只用工程术语，不使用这些说法做叙述词。
- 企业版内部对员工与对外对采购方的关注点不同（员工：支撑与归属；采购方：组织能力与 ROI）——同一引擎，不同侧重，但不得给出两边都不成立的承诺。
- 移交与继承（Inheritance）涉及法律、密钥托管与触发机制，后期单独立项；前期先用备份与恢复闭环验证这一条是否真能兑现。

## 9. 演进路线（待细化）

- **P0 切入点**：目录接入 + 数据接口 + 备份；单 Agent 组队；pr-helper 作为首个执行 Agent 跑通协议。
- **P1 协作**：A2A 组织结构与人工处理队列；Skill 安装/权限收窄；MCP 连接器市场雏形；2–3 个矩阵产品纳入。
- **P2 双形态**：企业数据域多租户 + 能力认证 + 任职资格校验流程；个人的备份清单与叙事日志；bayjf 对外签名目录。
- **P3 移交**：移交协议、密钥托管、合规与法律框架；全矩阵生态完成。

## 10. 开放问题（Open Questions）

1. 执行 Agent 协议是直接复用 A2A 标准的超集，还是自定义最小协议？
2. 备份清单的加密与密钥托管：纯本地密钥 vs 可恢复托管，如何取舍？
3. 企业版的计费单元：按组织结构还是按席位？
4. 个人与企业数据域共存时，授权粒度与审计呈现如何设计？
5. 外部 Agent 接入的信任分级与沙箱边界？
