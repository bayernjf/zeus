## 1. 结论摘要

| 等级 | 条数 | 一句话 |
| --- | --- | --- |
| A（高危） | 12 | 集中在三处：**治理状态可被后续操作抵消**（吊销复活、nonce 重放、撤回复活）、**配置声称生效实际未接线**、**并发与取消的时序漏洞** |
| B（中危） | 34 | 集中在错误分类（HTTP/传输层）、指标账不平、超时与背压缺失、非原子写入 |
| C（低危） | 22 | 类型说谎、死代码、注释与实现漂移、无界增长、配置覆盖不全 |

**整体判定**：内核主干（派发、聚合、签名、数据域读路径、持久化往返）结构扎实，安全边界在"主路径"上成立；问题几乎全部出现在三条支线上——

1. **重入路径**（重新注册、重连、重新整理、重新导入）：进入系统的入口做了守卫，**再次进入**的入口没做。A-02 / A-05 / A-06 是同一个形状。
2. **配置到内核的传递**：env 解析层写了校验和拒启，装配层少透传一个字段，于是"设了的限额"变成"以为设了的限额"。A-01 是这一条。
3. **异步时序**：意图落表晚于分支派发、信号量释放晚于可能抛出的回调、SSE 错误监听缺失。A-10 / A-11 / B-03 是同一个形状。

**先修这五条**（理由见 §8）：A-01、A-02、A-05、A-06、A-10。

## 3. A 级缺陷（12 条，已逐条复读源码确认）

> **复检结果（2026-10-01）：12 条已全部修复**。每条修复前均做缺陷植入验证（临时让守卫失效、确认新增测试变红、再恢复），commit 见各小节标题。§8 附执行结果与 A-12 白名单口径。

### A-01 并发上限配了但没接线，运维以为的保护不存在 ✅ 已修复（`87056a0`，2026-10-01）
`src/state/boot.ts:637` 解析 `ZEUS_MAX_CONCURRENT_PER_VASSAL`（非法值按注释"宁可拒启"处理），`src/http/serve.ts:72-77` 却只把 `maxConcurrentBranches` 与 `branchQueueLimit` 透传给 `bootKernel`，`maxConcurrentPerVassal` 在中途丢弃；内核侧 `src/orchestrator/orchestrator.ts:168-177` 实际认这个字段。
**影响**：运维设了这个值并通过启动校验，运行时永不生效——这正是 `boot.ts:617-619` 注释点名要避免的"读作保护、实则不存在的限额"。同时 #9 分流的 per-vassal 饱和信号恒为空。
**建议**：`serve.ts` 补一行透传，并加一条"设了该值时编排器收到该值"的装配断言。

### A-02 重新注册覆盖吊销状态，撤销可被一次注册抵消 ✅ 已修复（`bb9a38b`，2026-10-01）
`src/registry/registry.ts:120` 无条件 `entries.set(card.name, {... revoked: false})`；`importState`（:212）对快照零校验直接重建 Map。
**影响**：吊销后再次 POST 同名卡片即复活，并可换掉 `taskUrl` 与 `token`（流量与凭据重定向）。同名不同 `cardUrl` 也能静默顶替已注册条目。与"吊销是永久的"（`signing.ts:198-204`）语义冲突。
**建议**：吊销作粘性状态；恢复需显式 `reinstate` 并留审计。

### A-03 写凭证 nonce 淘汰时不落盘，崩溃后可重放 ✅ 已修复（`4fe069a`，2026-10-01）
`src/realm/grant.ts:143-153`：`if (!evicted) this.onChange?.()`——账本满触发淘汰时不触发持久化。
**影响**：刚消费的 nonce 在磁盘上缺失，崩溃重启后该凭证可重放。与同文件 :113-116 注释"崩溃丢掉的 nonce 就是可重放的凭证"直接矛盾。
**建议**：淘汰同样触发 `onChange`；或导出时按 FIFO 顺序截断，保证磁盘集合是内存集合的超集。

### A-04 跨域授权的 nonce 防重放是空转 ✅ 已修复（`5747bc1`，2026-10-01）
`src/realm/authorization.ts:171/196/221/259/269`——`seenNonces` 只在 `issue()` 判重与导入导出时使用，`verifyDomainGrant`（:32-62）与 `decideRealmAccess` 从不查询；`DomainGrantState.spentNonces` 是只写字段。
**影响**：文件头注释宣称"已消费凭证不可重放"，该保证在此层不存在。
**建议**：把消费账本接进决策路径，或直接删除该字段与对应注释。

### A-05 数据域重连改写只读态与域类型 ✅ 已修复（`b193d0d`，2026-10-01）
`src/realm/store.ts:120-141`：重连只比较 tenant（:120-124），不比较 `type`，且 `readOnly: opts.readOnly ?? false` 覆盖 previous。
**影响**：① 无 tenant 的企业域可用 `type:'personal'` 重连，企业写闸门随之消失；② `boot.ts:513-519` 用 `realmRoots` 重连时把快照里 `readOnly:true` 的挂载降级为可写；`vault/inventory.ts:133` 的校验路径同样以可写方式重挂。
**建议**：重连比较 `type`；`readOnly` 单调收紧（一旦只读，永远只读）。

### A-06 撤回的事实可被整理流水线复活 ✅ 已修复（`054a9fe`，2026-10-01）
`src/memory/memory-store.ts:109-117` 与 `src/memory/consolidate.ts:181-224`：`sameKey` 过滤掉 `retracted` 后，原 claim 在 :212-224 被当作**新事实**重建，事件日志仍在。
**影响**：`retractFacts` / `forgetSubject` 的成果在下一次 `consolidateRealm`（意图终态自动触发）后被抵消，已撤回内容重新进入事实库与检索索引。遗忘权在自动整理面前失效。
**建议**：整理期维护 tombstone 抑制集，撤回主体在墓碑存在期间不重建。

### A-07 日记渲染不排除已撤回事实，并落盘 ✅ 已修复（`79b20a9`，2026-10-01）
`src/diary/build.ts:79-84`：fact 过滤只判 `realmId` +（provenance 命中或 `updatedAt` 当日），不排除 `status === 'retracted'`。
**影响**：被撤回内容经 `persist.ts:21` 写回数据域文件，形成相对于记忆库的二次留存，且与 A-06 叠加。
**建议**：过滤加 `status !== 'retracted'`，并补一条"撤回后生成的日记不含该事实"用例。

### A-08 MCP 客户端不按 JSON-RPC id 匹配响应 ✅ 已修复（`f20ef18`，2026-10-01）
`src/mcp/client.ts:70`：`responses.find(r => 'result' in r || r.error)`，不看请求 id。
**影响**：SSE 多帧、乱序，或服务端在结果前插入通知帧时，返回错配结果；`tools/call` 可能拿到另一次调用的产物。这是静默的错误答案，不是报错。
**建议**：按 `r.id === id` 匹配，无匹配时 fail-loud。

### A-09 连接器声明空权限即绕过能力收敛 ✅ 已修复（`e9bbb64`，2026-10-01）
`src/mcp/connectors.ts:70`：`if (record.permissions.length > 0)` 才做能力裁剪；`callTool`（:129）只校验**存储**的 capabilities，`importState`（:151）可注入任意 capabilities。
**影响**：不声明任何权限的连接器，握手发现的全部工具均可调用——最小权限边界可被"不声明"绕过。
**建议**：空权限 = 空能力（fail-closed）；调用时按 permissions 重新推导而非信任存储值。

### A-10 并发槽位租约存在泄漏窗口 ✅ 已修复（`a518a88`，2026-10-01）
`src/orchestrator/orchestrator.ts:384` acquire 成功后，:399 `metrics.branchStarted`、:400/:404 `emit`、:405 `onDiverted` 均在 `try/finally`（:408-412）之外。
**影响**：任一抛出则 `release()` 永不执行，全局并发闸逐步耗尽直至死锁。`onProgress`（`boot.ts:389-394`）会做 SSE 广播 + 审计写入 + 记忆合并，完全可能抛。
**建议**：把 acquire 之后的所有语句纳入 try；或把 `release` 做成"一旦 acquire 成功即注册到 finally"的结构。

### A-11 取消触达不到在飞分支 ✅ 已修复（`f16a6de`，2026-10-01）
`src/orchestrator/orchestrator.ts:238` 在 fanOut **全部完成后**才 `intents.set`，而 `cancelIntent`（:338）从同一 map 读取。
**影响**：在飞期间调用取消必抛 `UnknownIntentError`；取消退化为事后补偿。且 :344-359 的取消结果不落库、不重算聚合——被取消分支的立场仍参与后续 `resumeBranch` 的 `recomputeResult`。过滤条件还要求 `branch.state` 存在，超时/无 state 分支永不可取消。
**建议**：意图在首个分支派发前以"最小可取消态"落表；取消结果回写分支状态与聚合。

### A-12 注册与连接器接口存在 SSRF 面 ✅ 已修复（`b1cf1a6`，2026-10-01）
`src/http/server.ts:268-300`：`POST /api/vassals` 接受任意 `body.cardUrl`，进程（持有 bearer 的一方）向该 URL 出站，无 scheme/主机白名单；同类面在 `POST /api/connectors`（:1375，任意 `endpoint`）、`/connect`（:1410）、`/tools/:name/call`（:1434）。
**影响**：可指向 `169.254.169.254` 等内网元数据端点；响应体经 `register()` 进入名册与快照。
**建议**：出站 URL 白名单，至少禁 RFC1918 / link-local / loopback；与 A2A 出站共用同一守卫。

## 7. 已核验成立的高风险面（防误报，也是资产）

审计必须同时回答"什么没坏"，否则清单一路加长却看不出系统哪里是硬的。以下经源码复核**确认成立**：

1. **数据域读路径逃逸防护有效** — `realm/store.ts:178-199`：`assertSafeItemId` → `resolve` → `isInsideRoot` → `lstat` 拒符号链接 → `realpath` → `isInsideRoot` 双检；`search` 不接受路径输入（走 connect 快照），无逃逸面。
2. **realmId 确定性** — `store.ts:118` 由 `sha256(realpath(root))[:16]` 派生。
3. **公开名册投影真剔除内部字段** — `roster.ts:114-126` 逐字段枚举，未拷贝 `cardUrl` / `taskUrl` / `healthDetail`；`Omit` 类型在 `RosterEntry` 新增必填字段时会编译报错（fail-loud）。
4. **签名链 fail-closed** — `signing.ts:331-432` 逐级返回 reason，无静默通过；`Ed25519Verifier` 缺 key/异常均返回 false。
5. **派发不泄漏凭据** — token 只经 `client.ts:67` 写入 `Authorization` 头；错误路径与审计 `detail` 均不含 token；`http/server.ts:290` 与 `redactConnector`（:2000）在出口剥离，`smoke-core.mjs:337-344` 有回归断言。
6. **Vault 加密无 nonce 复用** — `cipher.ts:39-41` 每次 seal 生成新 salt + 新 12 字节 IV，GCM tag 认证到篡改。
7. **技能闸门现算不缓存** — `skills/registry.ts:289` `activeProviders` 每次实时计算，卸载/弃用立即生效。
8. **上岗四道门现算不缓存** — `onboarding/commission.ts:271/322/332` 每次调 `verifyCommission`，吊销/带教作废后立即失效。
9. **撤回即时摘除检索索引** — `memory/recall.ts` 状态过滤 + 索引删除两道，仅 `active` / `disputed` 可入索引。
10. **MCP 服务端工具白名单在调用时强制** — `realm/mcp.ts:185-187` 与 `:192`，未声明工具无法调用，realmId 白名单即域边界，root 从不外泄。
11. **HTTP 鉴权分组正确** — 72 条写面路由全部挂 `requireBearer`，未配 `ZEUS_INTERNAL_TOKEN` 时整组不挂载（`server.ts:229`）。

### 10.2 本轮核验成立的高风险面（防误报，也是资产）

1. **Web 监督台未见注入落点**：全文 73 处 `innerHTML`；把**所有**模板插值机械过一遍（只保留表达式名含外部数据特征的候选）得 24 条，逐条为数字/布尔/内部串或已转义；转义器 `esc()` 覆盖 `& < > " '` 五类（`index.html:485-487`），`badge()`/`emptyRow()` 在内部就转义（`:503-504`），DAG 与编制两个"先拼串再整体注入"的 builder 逐行读过，节点 id、状态、关键路径均 `esc` 或 `.map(esc)`。**结论是"扫过且没找到"，不是"假定安全"。**
2. **CORS 是 fail-closed**：白名单精确匹配（`server.ts:179`、`:550`），默认**完全不发** CORS 头（实测带 `origin: http://evil.example` 请求 `/api/state` → 200 但响应里没有任何 `Access-Control-*`），非白名单源的预检 `OPTIONS` → **404**；命中时才发 `Access-Control-Allow-Origin` + `Vary: Origin`（`:551-552`）。
3. **鉴权矩阵实测六个端点**：`/healthz`、`/api/roster/public`、`/api/roster/keys` 无 token 即 200（公开面按设计），`/api/roster`、`/api/state`、`/api/domains` 无 token 一律 **401**、带 bearer 200。公开名册响应体核对：`scope:"public"`、`entries:[]`，无 revoked 行、无内部端点字段。
4. **终端监督台的凭证与破坏性动作政策是对的**：明确**拒绝** `--token` 旗标并说明理由（旗标在 `ps` 里可见，`src/tui/cli.ts:47`），token 只从 `ZEUS_INTERNAL_TOKEN` 进；撤销名册条目与跨域授权都过 `y/N` 确认（`src/tui/commands.ts:102`、`:104`；`runner.ts:52`、`:68`、`:114`），注释直说"确认后就和 curl 走同一条审计"。
5. **分层纪律仍在**：全库唯一 fastify 引入点仍是 `src/http/server.ts:2`。

### 10.3 仪器可信度：为什么"连上了"这句话需要一条对照

`file://` 页面能读到跨源正文这件事，**不能**直接当成"浏览器允许 file:// 跨源"。所以同一次会话里做了对照：把同一个 HTML 用 `http://127.0.0.1:8123` 起静态服务再打开，同一句 `fetch('http://127.0.0.1:8787/api/state')` 得到 `Failed to fetch`。**同一仪器、同一内核、只换页面源**——说明该浏览器确实执行 CORS，`file://` 的成功是该源的特殊待遇，而不是仪器放水。少了这条对照，B-35 会被误写成"Web 监督台可用"。

### 13.4 B-44 的半修：病灶原来是吞吐，不是内存（2026-10-06）

- **定位**：`ConcurrencyMetrics` 每结束一条分支，就对该 Agent 的**全部**历史重算一次分位（四次 filter + 一次 sort）。所以"台账只增不减"首先表现为**派发越跑越慢**，其次才是内存。库内 harness（同一 mock 派发、按批计时）实测：挂 metrics 时 100 条/批的边际成本从 353ms 涨到 1600 条处的 **3873ms**，比率 **12.07×**；不挂 metrics 的同负载对照 **0.79×**（平）。这条对照是必要的——没有它，"变慢"可能只是 mock 自身的噪声。
- **改法**：① 分支历史窗口封顶（默认 1000 条/Agent，构造参数 `historyWindowBranches`）；② 计数改为全时 O(1) 累加（`src/orchestrator/metrics.ts:215-215 #totals`），`snapshot()` 不再扫任何历史；③ 分位改为**读时惰性计算 + 缓存失效**，写路径只把缓存标脏。
- **改后复测**：同一 harness、同一负载，1600 条处 **17ms/批**、比率 **0.38×**。RSS 与状态文件斜率**没有变化**（仍 ≈2,074B/条），因为字节大头在意图结果里——实测拆分 **75% 是 intents（决策结果）、25% 是 requests（原始请求）**。这恰好说明剩下的一半不是工程问题：要不要删用户的决策记录，得先有人决定，转 deferred **#42**（2026-10-08 已实现出窗归档与 `evict` 开关，见 handoff Active work 145）。
- **语义变更（如实记账）**：顶层与 per-vassal 的 `calls/completed/failed/timedOut/canceled` 仍是**全时**，#9 分流读的 `failureRate` 也仍是全时；只有 `latency.*` 分位改为覆盖最近 ≤2×window 条。基数不藏：`latency.count` 说出本次分位用了多少样本，`historyWindow.trimmedBranches` 说出被窗口丢掉了多少条。"超过 2× 才整段裁"是刻意的摊还，避免每条都 shift。
- **验证**：新增 `tests/metrics-history.test.ts` 6 例（窗口封顶、全时计数不因裁剪而缩、canceled 不参与失败率、缓存必须随新样本失效、无匹配 start 的分支不改任何账、冷/热台账边际成本对照）。两处缺陷植入各打红 **1** 例：把窗口条件改成恒假 → 窗口那例红；删掉缓存失效那两行 → 失效那例红；植入后源文件逐字节复原、sha256 相同。计时那条只是粗护栏（阈值 6×），性能结论以 harness 读数为准。
