# Zeus UI 设计草案（UI Design Draft）

> 状态：**历史（设计草案，2026-09-29）**。本文只记录候选方案与取舍顺序，不是立项结论；立项条件、缺口论证与触发条件以 [deferred-items.md](deferred-items.md) **#34** 为单一事实源。
> 约束（四个方案共同遵守）：UI 只消费现有 HTTP API 与 SSE，内核零改动；不引入 BFF 层或界面私有逻辑；定位是"监督台"（人是决策者），不是全能控制台；每个写操作都必须能在审计日志回读、与直接调 API 等价。
>
> 界面基础契约（design token 三层模型、light/dark 与 TUI 子集、i18n key/ICU/资源完整性、无裸值与审计等价的校验闸门）见 [design-ui-foundations.md](design-ui-foundations.md) v0.1（现行）。任何方案开工第一个页面前先实现该规范；本文不重复其内容。

## 0. 推荐落地顺序

**D（过渡，低成本验证交互）→ A（Web v1，M3 收尾后）→ C 或 B（按首个真实用户是企业还是个人二选一）。**

- D 与 A 不互斥：D 在触发条件未满足前即可做，用于验证扇出 / 裁决的真实交互形态。
- A 之后不自动扩 B：B 的每个视图都必须由真实使用需求触发，避免工作流未定型时大面积返工。
- C 与 B 的分叉由用户类型决定：企业场景优先 C（对外信任证据），多角色内部治理优先 B。

## 方案 A：单页实时监督台（作战室模式）

一个页面 = 一次扇出的实时现场，SSE 驱动，默认全屏。

```
┌─ Intent intent-9f3a ─ deployment-health ─ ⏱ 00:12 ─ [Cancel] ─┐
│  状态: partial (2/3 completed, 1 needs-driver)                 │
├───────────────────────────────┬───────────────────────────────┤
│  分支                           │  聚合 / 决策                   │
│  ● pr-helper   completed  2.1s │  rule: majority               │
│    └ deployment-health plan    │  positions: []                │
│  ● agent-dev   completed  3.4s │  conclusion: null             │
│    └ report: 8/9 checks ok     │  ┌─────────────────────────┐  │
│  ◐ loom        running…   9s   │  │ needs-driver: no stance │  │
│                               │  │ [View escalation]       │  │
│  [events ▾]                    │  └─────────────────────────┘  │
├───────────────────────────────┴───────────────────────────────┤
│  审计时间线  dispatched ×2 · vassal-revoked · 12:04:31 …       │
└───────────────────────────────────────────────────────────────┘
```

- **优点**：与"高并发扇出 + 人做裁决"的核心定位精确对应；信息密度高、决策路径短（一键进 escalation 做 approve / reject）。
- **缺点**：只管当下这一次，没有历史回顾、组织 / 技能管理；高频实时刷新对前端要求高。
- **端点依赖**：`POST /api/intents`、`GET /api/intents/:id`、`GET /api/intents/:id/events`（SSE）、`POST /api/intents/:id/cancel`、`GET /api/escalations/:id`。
- **定位**：Web v1，触发条件满足后的最小可用版。

## 方案 B：按角色分区的多视图工作台

左侧导航按角色切视图：监控 / 裁决 / 名册 / 技能 / 审计 / 组织。

```
┌────────┬──────────────────────────────────────────────────┐
│ ▣ 监控  │  裁决队列 (3 pending)                             │
│ ▣ 裁决  │  ┌────────────────────────────────────────────┐  │
│ ▣ 名册  │  │ esc-21 · intent-9f3a · input-required      │  │
│ ▣ 技能  │  │ Missing: owner, repo                       │  │
│ ▣ 审计  │  │ [Approve + resume] [Reject] [Edit params]  │  │
│ ▣ 组织  │  └────────────────────────────────────────────┘  │
│        │  ┌────────────────────────────────────────────┐  │
│        │  │ esc-22 · memory-dispute · 2 conflicting…   │  │
│        │  │ [Resolve]                                   │  │
│        │  └────────────────────────────────────────────┘  │
└────────┴──────────────────────────────────────────────────┘
```

- **优点**：覆盖完整治理面——escalation 分流（缺参 / 冲突 / 记忆争议）、名册吊销、技能 harden、审计回读均有入口；企业采购演示形态。
- **缺点**：页面多，工作流未定型时返工面大；易膨胀成全能控制台，偏离 #34 第一版只做三件事的口径；开发量约为方案 A 的 3–4 倍。
- **定位**：v2，方案 A 跑通且真实用户出现后按视图逐个扩展，不一次性建全。

## 方案 C：双门户——对外只读门户 + 对内操作台

利用 `GET /api/roster/public`（签名名册）与公开密钥端点天然区分两个受众。

```
公开门户 (无鉴权)                    内部操作台 (bearer)
┌─────────────────────┐            ┌─────────────────────┐
│ 在册 Agent (已验签)  │            │ 意图 / 裁决 / 授权    │
│  ● pr-helper  active │            │ (方案 A 或 B)        │
│  ○ loom       revoked│            │                     │
│ 根公钥指纹           │            │                     │
│ 审计公开摘要         │            │                     │
└─────────────────────┘            └─────────────────────┘
```

- **优点**：把"数据主权 / 信任可验证"做成对外证据——任何人可验签名、看吊销状态；对内是操作面。与产品画像中 bayjf"对外签名目录"同源、可复用。
- **缺点**：公开门户涉及对外暴露口径，与 A5 / bayjf 工作耦合；一个产品两个界面，维护成本高。
- **端点依赖**：`GET /api/roster/public`、`GET /api/roster/keys`（公开面）+ 内部 bearer 面。
- **定位**：企业场景先行时说服力最强；个人场景过重。

## 方案 D：终端 TUI / IDE 插件（不做 Web）

承认当前使用者是开发者，用与 `scripts/` 同风格的零依赖 TUI（或 IDE 插件）直连 API。

```
 Zeus ─ dev
 1 intents active   3 escalations pending
─────────────────────────────────────
 intent-9f3a  deployment-health   partial
   pr-helper  ✓ 2.1s
   agent-dev  ✓ 3.4s
   loom       ⠋ running (9s)
─────────────────────────────────────
 [1] approve esc-21  [2] reject  [q] quit
```

- **优点**：零浏览器依赖、零新基础设施；与现有脚本和 CLI 工作流一致；开发最快；仍满足"所有能力走 API"。
- **缺点**：非技术用户不可达、企业采购不认可；图谱与历史趋势等可视化能力弱。
- **定位**：Web UI 之前的过渡方案；可在 #34 触发条件未满足前先做，低成本验证交互、不锁死未来形态。

> **实现进展（2026-09-30）**：方案 D 最小切片已落地（`npm run tui` → `dist/tui/cli.js`，源码 `src/tui/`）。零依赖行式终端监督台，只消费现有 bearer HTTP 面、内核零改动、无新增端点：只读监控（内核状态 / 并发指标 / 名册）、escalation 裁决（`a/x/s` approve/reject/resolve，均带 y/N 确认）、名册吊销（`d`，y/N）。严格按 [design-ui-foundations.md](design-ui-foundations.md) 实施：状态→语义 token→ANSI 一一映射（`tokens.ts`，`NO_COLOR`/非 TTY 不着色、未知状态降级不臆造）、zh-CN/en 双资源与占位符对齐由测试断言（`messages.ts`/`format.ts`）。25 项 TUI 单测（i18n/tokens/命令解析/纯渲染/控制器写操作）。此为过渡验证，不改变 deferred #34 的 Web 立项条件。

## 技术口径（适用于 A / B / C）

- 轻量单页栈（如 Preact + Vite），直连现有 HTTP 端点 + SSE；不设 BFF、不加新的内核端点。
- 鉴权沿用 bearer（H2 面）与公开面无鉴权的现有划分；前端不持久化令牌到非 0600 位置。
- 验收：① 每个写操作都能经 `GET /api/audit` 回读；② 同一操作在 UI 与直接 curl 下审计记录等价；③ 内核侧零改动、无新增测试以外的通道。
