# Agent 时代的系统互联与确定性边界设计

> 状态：**现行（设计稿 v0.3，2026-09-23，补连接/工具设计/护栏三层成熟度）**。实施进度记 [handoff.md](../handoff.md)，本文只写设计与判断。
> 性质：这是**架构立场文档**，回答"AI 时代多个系统之间怎么沟通、边界划在哪"；具体协议契约看 [design-vassal-protocol.md](design-vassal-protocol.md)、[design-memory-consolidation.md](design-memory-consolidation.md)、[design-decision-backend.md](design-decision-backend.md)。
> 本文是对 Zeus「叙事化概念必须与真实可执行工程原语同构」这一设计哲学在系统互联层面的展开。

## 1. 问题

传统分布式 / 微服务通过 RESTful 暴露接口、彼此调用；系统设计的核心是"暴露哪些接口去和别的系统联动"。问题：AI 时代，当多个系统可以通过 Agent 沟通时——

- 这是不是一种新的架构形式？
- 能不能（以及在哪种意义上）重构传统系统的形态？

## 2. 核心结论

**Agent 不会成为新的 REST，它会成为新的编排 / 集成层；底层确定性原语不会消失，反而更重要。**

三点支撑：

1. **每代架构只在某个边界上换耦合方式，不抹掉下层。** REST 当年也没替代函数调用，只是把边界上的重型 RPC 换成更松的资源耦合。
2. **Agent 的价值在更高的边界**：过去必须靠"人"粘合的地方——对方系统不掌握、目标开放、会出现没预料到的情况。接口从"怎么调"（method/schema）上移到"要什么"（task/goal）+ 能力声明（Agent Card），允许运行时延迟绑定与协商。
3. **自然语言是有损、非确定性契约。** 事务完整性、幂等、权限、对账无法建立在"模型这次理解对了"之上；LLM 调用更贵、更慢、会失败、难复现，全链路 Agent 化在工程与成本上都不成立。

因此新形态不是替换，是**两层**：

```
        ┌─────────────────────────────────────┐
  智能层 │ Agent：目标协商 / 编排 / 异常消解 / 集成 │  语言、非确定、跨系统粘合
        └───────────────┬─────────────────────┘
                        │ 调用的仍是确定性能力
        ┌───────────────▼─────────────────────┐
  原语层 │ Function / API / MCP tool / 状态机    │  契约、确定、可验证、可回放
        └─────────────────────────────────────┘
```

Zeus 已无意识地按此分层：**MCP** 接近带 schema 的 REST（确定性工具/资源边界）；**A2A** 是有状态任务委派（更靠上）；**LLM/Agent** 只在契约够不到处消解歧义；而事实、provenance、快照、replay 全是确定性原语。Agent 越往上自由，底下的确定性基座越要硬。

## 3. 边界怎么划

**核心判据：用「错了能不能反悔 + 代价多大」分，而不是用「难不难」分。** 难的事未必交给 Agent；不可逆的事哪怕简单也钉死。沿四轴判断：

| 轴 | 交给 Agent | 钉死成契约 / 原语 |
|---|---|---|
| **可逆性** | 可逆、可补偿：读数据、生成草稿、改本地副本 | 不可逆：扣钱、删除、对外发送、生产变更（动作钉死，Agent 只准备建议，执行走凭证 + 授权） |
| **确定性需求** | 允许近似：摘要、分类、语义召回、方案生成 | 要求同一结果：金额计算、规则判定、权限校验、状态流转 |
| **可验证性** | 目标开放、对方形态不定、无法预先建模（协商） | 能给结构化 schema、能写测试/对账（做 MCP tool/API；Agent 决定后执行仍须重过契约） |
| **爆炸半径** | 影响私有草稿 | 影响共享状态、他人、钱、合规（边界处审计 + 可回放 + 拍板点） |

判据辨析：一个输出错了，是"**质量差一点**"还是"**事实就错了**"。后者必须确定性。

### 3.1 边界本身：一道确定性闸门

```
开放目标 ──Agent（协商/拆解/判断，非确定，可错）──▶ 结构化意图
                                                        │
                                         过一道确定性闸门：校验 schema / 权限 / 幂等
                                                        │
                                             ┌──────────┴──────────┐
                                        可逆动作              不可逆动作
                                         直接执行           人类授权 + 凭证
                                             └──────────┬──────────┘
                                                        ▼
                                             确定性原语执行 + 全审计
                                                        ▌
                                                 结果回流，Agent 再解读
```

边界不是一条横线，是"**结构化意图 → 确定性闸门**"这个收口。Agent 在闸门左侧自由，右侧一步进不去。这与记忆协议"追加与修改分离"同构：**自由地产生候选，严格地改变事实。**

### 3.2 永远不交给概率（钉死清单）

1. 权限与数据域边界——谁能碰什么，数据二极管；
2. 不可逆动作的触发与凭证；
3. 钱、计数、规则性事实的计算；
4. 状态机的合法流转、幂等键；
5. provenance、快照、审计、回放——追责链路；
6. 注入 / 越界检查——非可信数据进入上下文前。

### 3.3 可以交给 Agent

目标理解、任务拆解、方案生成、语义匹配、把模糊信息**结构化**、异常时初步诊断并给人选项、把结果讲成人话。多在"**理解与表达**"层，不在"**决定与执行**"层。

## 4. 与现有插座的关系

新产品要与 Zeus 联动，**不从头做**，按形态选现成插座（立国三纲）：

- **MCP（连接）**：新产品是工具 / 数据源、无状态、Zeus 单向调用 → `ConnectorRegistry.declare` 声明即用，`mcp:<tool>` 最小授权，`revoke` 断权。最轻。
- **A2A / 封臣协议（协作）**：新产品要作为有状态 Agent 参与决策、回战报、在不可逆操作上升级 → 暴露 Agent Card + fealty，经 `/api/vassals` 登记，过定型全链路。
- **Skill（技能）**：能力抽象而非传输；接入后把能力登记成 Skill，Orchestrator 按技能自动组队。

MCP 轻但无状态单向；A2A 重但有完整协作与治理闭环。

## 5. 锋利的说法

你不是在划分"哪些功能用 AI"，而是给每个动作定三件事：**它的契约是什么、它可逆吗、错了谁有权拍板。** 三件说不清，边界就没划好——宁可钉死，不交给 Agent。REST 时代设计"系统暴露哪些接口"；Agent 时代设计"**哪些决定交给运行时协商，哪些必须钉死成契约，以及交界处谁拍板、出错怎么回放**"。难点从定义接口上移到划确定性边界。

## 6. 保留意见（软肋）

这层智能粘合的可靠性，取决于非确定性能否被严格关进监督、权限、回放的笼子。具体软肋是**闸门本身**：

- 校验太弱 → Agent 错误漏进执行；
- 校验太重 → 退回写死所有接口，Agent 形同虚设。

真正的工程功夫在这道闸门的"**最小但充分**"。因此近中期更现实的形态是 **Agent 做面、确定性服务做骨** 的混合体，而非"全 Agent 互联"。

## 6A. 行业现状：让软件"对 AI 原生可操作"的主流形态

> 本节是外部行业现状（截至 2026 年初），与 §2–§5 的内部立场对照：Zeus 的设计与主流范式同构，差异在更强调数据主权与可追责。

核心一句话：**把软件每一项能力做成 Agent 可调用的"工具"，GUI 退化为众多客户端之一，而非唯一入口。** 五种主流实践：

1. **Function Calling / Tool Use（地基）**：模型不操作界面，而输出结构化工具调用（函数名 + JSON 参数），软件端执行后回喂结果、模型继续推理。"点按钮→一次调用"变为"模型自己决定调哪个工具、传什么参"。所有主流模型的标准能力。
2. **MCP（工具接入标准化，2025 起事实标准）**：以标准协议统一暴露 tools/resources/prompts，替代每个 Agent 接系统都要写的定制胶水。Zeus 的 `ConnectorRegistry`/`McpClient` 即此。
3. **Agent Loop（执行框架）**：循环"规划→调工具→观察→再规划"直到意图完成；载体如 Claude Agent SDK、OpenAI Agents SDK、LangGraph，开发者只定义工具集。
4. **Computer Use / GUI Agent（兜底）**：软件只有界面无接口时，让模型看截图直接操作鼠标键盘（Claude Computer Use、OpenAI Operator）。是退路非首选——脆弱、慢、易错，能给接口就不给截图。
5. **工程化护栏（生产必备）**：结构化输出、最小权限/OAuth、危险动作人工确认（HITL）、全程可观测回放。对应封臣协议"不可逆 execute 必须升级 approve/reject"。

### 6A.1 "对 AI 原生"的设计原则

```
旧：用户 ──鼠标/触屏──▶ UI ──调用──▶ 业务逻辑/DB
新：用户 ──意图──▶ Agent ──工具调用──▶ 业务逻辑/DB
                  ▲                 （同一套能力）
              能力以 schema 暴露    UI 仍在，但只是另一个客户端
```

三条转变：

1. **API / Headless 优先**：每个功能先有可程序调用、带 schema、带鉴权的形态，UI 是上面一层皮；
2. **能力即工具**：暴露"能做什么"而非"有哪些页面"；
3. **Agent 做意图理解，业务逻辑确定性执行**：模型把模糊意图变为结构化调用，真正改数据走确定性后端与权限闸门，语言不直接产生副作用（即 §3 确定性闸门）。

### 6A.2 关键区分：做了 MCP ≠ 好用（三层成熟度）

协议只解决"**能连**"，它是必要入场券而非充分条件。一个暴露 200 个粗粒度工具、参数含糊的 MCP server，模型反而更容易调错。落地按三层递进：

| 层 | 解决的问题 | 内容 | 不做的后果 |
|---|---|---|---|
| **L1 连接（协议层）** | 能连、能被发现 | 能力按标准暴露：MCP / Function Calling | Agent 根本接不上 |
| **L2 工具设计（可用性层）** | 好用、调得对 | ① 粒度合适（一工具一件清楚的事，不粗到猜、不碎到调十步）；② schema 严格 + 描述准确（类型/必填/取值/何时用）；③ 结果结构化、错误可行动（报错即知下一步）；④ 能力可组合 | 连得上但频繁调错 |
| **L3 护栏（安全层）** | 安全、可追责 | 最小权限 / OAuth、不可逆动作 HITL 确认、全程审计回放 | 一次调错即真实损失 |

本质：过去为"人点按钮"做的可用性设计，现在要为"模型读 schema 做决策"重做一遍（L2）。

**传统软件重构路径**：

```
1. Headless/API 化：业务逻辑从 UI 后解耦（确定性内核是资产，保留）
2. 套标准协议（MCP/A2A）：能力可被发现调用          ← L1
3. 重新设计工具面：粒度 / schema / 描述 / 错误 / 组合 ← L2
4. 加护栏：权限 / HITL / 审计                        ← L3
```

一句话：**MCP 是"插座标准"，但插上后好不好用取决于"插头"（能力切分）。** 不重写业务内核，只重构"对外暴露能力"那一层——从面向页面/鼠标改为面向工具/schema；UI 不删除，退为一个客户端，Agent 是新增的一等公民入口。
